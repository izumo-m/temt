# temt 設計

temt の設計。何をどう作るかを書く。判断の理由は、手順だけでは意図が読めない
ところにだけ短く書く。判断の優先順位は [overview.md](overview.md) にある。
設計は [discussions/](discussions/) で議論し、決まった内容をこの文書と design/、
apps/ に反映し、議論を終えたら記録を `done/` へ移す。`done/` は凍結した過去の
記録で、後から書き換えない。いまの仕様と食い違っていても、この文書と design/、
apps/ を正とする。
利用者向けの手順は [usage.md](usage.md) に、アプリの作り方は [apps.md](apps.md) に
ある。リソースや仕組みごとの詳細は [design/](design/) の分野別のファイルにあり、
この文書から辿る。temt と一緒に配るアプリの使い方と設計は、アプリごとに
[apps/](apps/) にある。

作るのは、サービスを 1 つ用意し、インスタンスを起動し、ssh でログインし、アプリを
入れ（`deploy`）、インスタンスを AMI にし（`bake`）、終了し、片づけるまでの仕組み
である。使われていないインスタンスが自分で終了する仕組みは、temt と一緒に配る
アプリ `idle-shutdown` として作る（[apps/idle-shutdown.md](apps/idle-shutdown.md)）。

## 名前

サービスとは、ひとつの用途のために立てる EC2 インスタンスの定義である。1 つの
サービスは 1 つの設定ファイルで定義し、インスタンスは 1 台とする。同じ用途を設定
違いで複数立てるときは、別の名前のサービスにする。

サービス名 `<svc>` は、英小文字で始まり、英小文字・数字・ハイフンが続き、英小文字か
数字で終わる。`temt` がこの規則で引数を検査する。

リソースの名前は、すべて `temt-<svc>` から導く。以下、この文字列を `<名前>` と
書く。`<名前>` は 64 文字以内とする（IAM ロール名の上限）。

| 対象 | 名前 |
| --- | --- |
| インスタンスの Name タグ | `<名前>` |
| 起動テンプレート | `<名前>-template` |
| State Manager の関連付け（sshd の待ち受けポート） | `<名前>-sshd` |
| セキュリティグループ | `<名前>` |
| IAM ロールとインスタンスプロファイル | `<名前>` |
| キーペア | 設定ファイルの `KeyName`。既定は `temt`。`keypair create` で作るときは、その引数 |
| 秘密鍵と公開鍵 | `~/.ssh/temt/keys/<キーペア名>`、`~/.ssh/temt/keys/<キーペア名>.pub`。ssh が使う秘密鍵は設定ファイルの `IdentityFile` |
| SSM パラメータの階層 | `/<名前>`。`destroy` がこの下をすべて消す |
| アプリの値と記録 | `/<名前>/<アプリID>/<キー>`。キー `deploy` はアプリの記録、`status` はアプリが書く状態 |
| ロールのポリシー | ロールのインラインポリシー `temt-<ポリシー名>`。ポリシー名は設定ファイルの `[[role.policy.<ポリシー名>]]`。`temt-ec2` はインスタンスそのものの権限で、設定ファイルに無ければ `apply` が既定を書く |
| インスタンスの上のアプリ | `/opt/temt/apps/<アプリID>/`。root の持ち物 |
| 設定ファイル | `~/.config/temt/<svc>.toml` |
| ssh の Host | `<名前>`（`~/.ssh/temt/config` の中のブロック） |
| known_hosts | `~/.ssh/temt/known_hosts.d/<名前>/` |
| AMI と、そのスナップショットの Name タグ | `temt-<svc>-<YYMMDDHHMM>`（`<svc>` は焼いたサービス。時刻はクライアントのローカル時刻） |
| クライアントのコマンド | `temt`。入れ方は問わず、PATH から探して呼ぶ |
| サービスのコマンド | `~/.local/bin/<名前>`。PATH にある `temt` に `--svc <svc>` を付けて実行するシェルスクリプト。`apply` が書き、`destroy` が消す。`<名前> ...` は `temt --svc <svc> ...` の別名 |

temt が手元の鍵のファイル名にするキーペア名（`KeyName` と、`keypair create`、
`keypair delete` の引数）は、英数字で始まり、英数字、`.`、`_`、`-` だけが続き、
`.pub` で終わらない、251 文字以内の名前とする。`keys/` の外を指せないよう、`/` など
を入れさせない。`.pub` で終わる名前は、他のキーペアの公開鍵のファイル名とぶつかる。
251 は、ファイル名の上限 255 バイトから `.pub` の 4 文字を引いたものである。

temt が作る AWS リソースには、temt が管理していることを示すタグ
`temt:service=<svc>` を付ける。キーペアはどのサービスにも属さないので、代わりに
`temt:keypair=<キーペア名>` を付ける。付けるタグはリソースによって
次のとおりである。

| リソース | タグ |
| --- | --- |
| インスタンス、そのボリュームとネットワークインターフェース、セキュリティグループ | `Name=<名前>`、`temt:service=<svc>` |
| AMI とそのスナップショット | `Name=<AMI の名前>`、`temt:service=<svc>`（`<svc>` は焼いたサービス） |
| 起動テンプレート、IAM ロール、インスタンスプロファイル、関連付け | `temt:service=<svc>` |
| キーペア（temt が登録したものだけ） | `temt:keypair=<キーペア名>` |

下の 2 行のリソースは名前を持ち、コンソールでも名前で見えるので、`Name` タグは
付けない。既にある AWS リソースに付いている、表に無いタグには、temt は触らない。

サービスを扱うコマンドは、`<svc>` をコマンドラインオプション `--svc <svc>` で
受け取る。`service list`、`instance list`、`ami list`、`ami prune`、`ami delete`、
`app list` は `--svc` を省け、`keypair` のコマンドは `--svc` を取らない。ほかの
コマンドは `--svc` が要る。

## リポジトリの構成

```
src/temt/       コマンド temt の Python パッケージ
src/temt/apps/  temt と一緒に配るアプリ
tests/          temt のテスト（pytest）
docs/           overview.md、usage.md、conf.md、apps.md、apps/、design.md、design/、discussions/
pyproject.toml  パッケージと依存の定義。uv が読む
uv.lock         開発用の環境（uv run）の依存の固定

```

## 利用者のホームに置くもの

```
~/.local/bin/
    <名前>                    サービスのコマンド。無ければ apply が書き、destroy が消す
~/.config/temt/               conf ディレクトリ。temt が作るならモード 700
    <svc>.toml                サービスの設定。無ければ apply が書く
    apps/<アプリID>/          deploy がアプリ ID で先に探すアプリ。利用者が置く
~/.ssh/temt/                  ssh ディレクトリ。モード 700
    config                    ssh の設定。apply が Host ブロックを足し、更新する。
                              ~/.ssh/config から Include する
    keys/                     鍵。モード 700
    keys/<キーペア名>         apply か keypair create が作る秘密鍵。モード 600。
                              keypair delete が消す
    keys/<キーペア名>.pub     その公開鍵
    known_hosts.d/<名前>/     インスタンスごとの known_hosts、current、.lock
    .config.lock              ssh の設定を書き換えるあいだ掛けるロック
```

サービスのコマンドは、次の 3 行のシェルスクリプトである。`temt` を PATH から探すので、
`temt` の入れ方や版が変わっても書き直さずに済む。

```sh
#!/bin/sh
# Written by temt apply for the service <svc>; temt destroy removes it.
exec temt --svc <svc> "$@"
```

`~/.ssh/config` の先頭に、目印のコメントと、ssh ディレクトリの `config` を指す
`Include` の 2 行を置く。無ければ `apply` が足す。

`deploy` がアプリ ID で指されたアプリは、conf ディレクトリの `apps/<アプリID>/` を
先に探し、無ければ temt と一緒に配るアプリ（パッケージの `apps/<アプリID>/`）を使う。
temt と一緒に配るアプリのために利用者のホームに置くものは無いので、temt を入れ直し
ても上げても、揃え直す手順は要らない。

### 場所を変える環境変数

conf ディレクトリと ssh ディレクトリは、それぞれ環境変数で変えられる。`--svc` を
付けたすべてのコマンドと `service list` が読む。`keypair` のコマンドは、鍵の場所を
決める `TEMT_SSH_DIR` だけを読む。`--svc` を省いた `ami prune` も、ロックの場所を
決める `TEMT_SSH_DIR` だけを読む。値が誤っていれば、確認を求める前にエラーにする。
`--svc` を省いた `app list` は、アプリの場所を決める `TEMT_CONF_DIR` だけを読む。

| 変数 | 場所 | 既定 |
| --- | --- | --- |
| `TEMT_CONF_DIR` | conf ディレクトリ | `~/.config/temt` |
| `TEMT_SSH_DIR` | ssh ディレクトリ | `~/.ssh/temt` |

絶対パスで書く。値の規則は [conf.md](conf.md#場所を変える環境変数) にある。どちらの
変数も、それを読むコマンドが起動のたびに読み、値は保存しない。`ProxyCommand` は、
2 つの場所を既定のままでも `proxy` に渡す（[design/ssh.md](design/ssh.md)）。

`TEMT_CONF_DIR` は、サービスの定義を読む場所を選ぶ。変えれば、次の実行から
`temt` のコマンドはその場所の設定ファイルを読む。ssh ディレクトリは場所を
またいで 1 つなので、どの場所で `apply` したサービスにも ssh でつながる。その
代わり、同じ `<svc>` の設定ファイルを 2 つの場所に持つことはできない（`apply` の
手順 1）。

`TEMT_SSH_DIR` は、ssh の設定・鍵・known_hosts を移すためのものである。`~/.ssh`
そのものは指せない。`apply` が ssh の設定に書く `IdentityFile`、
`UserKnownHostsFile`、`Include` は、その `apply` を実行したときの値で決まる。
`~/.ssh/config` の `Include` は 1 行なので、変えてから `apply` すると、前の ssh
ディレクトリにある Host には ssh でつながらなくなる。`apply` はそれらの Host を
挙げて警告する。前の場所に残ったものは `temt` が動かさず、`destroy` もそのとき
変数が指す場所だけを片づける。

この文書では、conf ディレクトリと ssh ディレクトリを既定の場所で書く。

## 設定ファイル

`~/.config/temt/<svc>.toml`。サービスの定義で、`--svc` を付けたすべてのコマンドが
読む。`--svc` を付けない `service list` は、すべての `<svc>.toml` を読む。形式、
項目と既定、`apply` が書く規則は [conf.md](conf.md) にある。
以下、設定ファイルの項目はテーブル名を省いて `InstanceType` のように書く。

設定ファイルは複数のマシンで共有するサービスの定義であり、マシンごとに違う ssh の経路は
持たない。それは環境変数 `TEMT_LOGIN` で与える。AWS のプロファイルは `AwsProfile` に
書けるが、マシンごとに違うなら `--profile` で上書きする。

`--svc` を付けたコマンドのうち `apply` 以外は、ファイルが無ければ `apply` を実行する
よう促して終了する（`destroy` を除く。「すべてのコマンドに共通の振る舞い」を見よ）。

`--svc` を付けたコマンドが使うプロファイルは、`--profile`、設定ファイルの
`AwsProfile` の順に決まる。決まれば、boto3 には `Session` の引数として、
aws-cli には `--profile` として渡す。決まらなければ、boto3 にも aws-cli にも
プロファイルを渡さず、資格情報は AWS の既定の規則（環境変数 `AWS_PROFILE` や
`AWS_DEFAULT_PROFILE`、環境変数の鍵、`[default]` プロファイルなど）で決まる。
このとき aws-cli を呼ぶ前に、環境変数 `AWS_DEFAULT_PROFILE` か
`AWS_PROFILE` があれば、boto3 が選ぶもの（`AWS_DEFAULT_PROFILE` が先）を、
aws-cli に渡す環境の両方の変数に入れる。aws-cli v2 は 2 つを boto3 と逆の順に
読むので、両方あって値が違うと食い違うからである。

リージョンは、boto3 には `Session` の引数として、aws-cli には `--region` として
渡す。aws-cli を呼ぶときは `AWS_PAGER` を空にする。

`--svc` を付けたコマンドのリージョンは必ず決まる。設定ファイルに無ければ
`ap-northeast-1` を使い、初回の `apply` がその値を書く。1 つの設定ファイルは 1 つの
インスタンスに対応するので、リージョンを変えるときは別の `<svc>` として立てる。

`--svc` を付けたコマンドは、どのリージョンを使うかを設定ファイルだけで決める。それを
確かなものにするため、`temt` は動き始めるときに、環境変数 `AWS_REGION` と
`AWS_DEFAULT_REGION` を自分の処理から取り除く。boto3 は `AWS_DEFAULT_REGION` だけを
読み、aws-cli は `AWS_REGION` を先に読むので、環境に残しておくと両者が別の
リージョンを向きうる。

`service list` と `app list` を除き、`--svc` を付けないコマンドは、設定ファイルを読まず、
プロファイルとリージョンを `--profile` と `--region` で決める。`--profile` を
省けば、プロファイルは AWS の既定の規則で決まる。リージョンは、aws-cli と同じく
`--region`、`AWS_REGION`、`AWS_DEFAULT_REGION`、プロファイルの `region` の順に
探し、決まらなければエラーにする。環境変数は取り除く前に控えておく。boto3 は
`AWS_REGION` を読まないので、temt が読んで渡す。1 回の実行で 1 つの環境
（アカウントとリージョン）だけを扱い、実行の初めに、`get-caller-identity` で得た
アカウントと、リージョン、プロファイルを 1 行で知らせる。プロファイルは、
`--profile` か環境変数 `AWS_PROFILE`、`AWS_DEFAULT_PROFILE` で選んだときだけ
名前を出し、選んでいなければ `(none)` と出す。boto3 は選んでいなくても
`default` と答え、そのとき資格情報は環境変数の鍵などから
来ていることがあるからである。`service list`、`sg list`、`sg add`、
`sg remove` は設定ファイルを読むが、AWS を呼ばないので、プロファイルも
リージョンも使わない。`--svc` を付けない `app list` も AWS を呼ばず、conf
ディレクトリの `apps/` と、temt と一緒に配るアプリだけを読む。

設定ファイルにアカウントは書かない。どのアカウントを使うかは資格情報で決まり、別の
アカウントの資格情報で `apply` を実行すれば、そのアカウントに新しく作る。ただし
`SubnetId` と `ImageId` はアカウントの中のリソースを指すので、別のアカウントで作る
ときは、これらの行を消してから `apply` を実行する（[conf.md](conf.md)）。

## AWS リソース

`apply` が、サービス 1 つにつき次の 6 つを、無ければ作る。キーペアを除く
5 つには、作るときに「名前」の節のタグを付け、既にあれば、そのタグが無ければ足し、
値が違えば直す。既にあるものは、ほかに次のように扱う。

- キーペア: 無ければ登録して `temt:keypair` を付けるが、あれば変えず、タグも
  足さない。
- IAM ロール: インラインポリシー `temt-<ポリシー名>` を設定ファイルに揃える。
  `temt-` で始まらないインラインポリシーと、管理ポリシーには触らない。
- インスタンスプロファイル: ロールが入っていることを確かめ、無ければ入れる。別の
  ロールが入っていれば、外して入れ替える。
- セキュリティグループ: 受信規則を設定ファイルに揃える。
- 起動テンプレート: 設定ファイルに合わせて更新する。
- 関連付け: 名前で探し、中身を設定ファイルに揃える。作ったときと中身を更新した
  ときは、実行を求める。

`destroy` は、6 つのうちキーペアを除く 5 つと、`/<名前>` の階層の下にある SSM
パラメータを消す。ロールは、付いたインラインポリシーをすべて消してから消す。
キーペアは複数のサービスで共有しうるので、`keypair` のコマンドで別に扱う。

`proxy` と `status` は、インスタンスの ID とパブリック IPv4 アドレスを、そのつど
`describe-instances` で探す。

起動テンプレートがあることを、サービスが `apply` されていて `destroy` されていない
ことの目印とする。`destroy` は起動テンプレートを最初に消すので、途中で失敗した
サービスも `apply` されていないとみなす。

**キーペア `<KeyName>`。** インスタンスにログインできる鍵は、このキーペアの鍵だけ
とする。手元の鍵（設定ファイルの `IdentityFile`）との揃え方と、一致しないときの
扱いは [design/keypair.md](design/keypair.md) にある。

**IAM ロール `<名前>`。** 信頼ポリシーは `ec2.amazonaws.com` だけを許す。
信頼ポリシーは書き換えない。権限は、設定ファイルの `[[role.policy.<ポリシー名>]]`
（[conf.md](conf.md#role)）から作るインラインポリシー `temt-<ポリシー名>` だけで、
管理ポリシーは付けない。IAM はロールに付いたポリシーをすべて足し合わせて評価する。
ポリシーは `apply` だけが付け、`deploy` と `app remove` はロールに触らない。

`temt-ec2` は、アプリに結びつかないインスタンスそのものの権限で、既定では、temt が
動くのに要る SSM エージェントの権限（Session Manager、Run Command、State Manager）
と、`/<名前>` の下の SSM パラメータの読み書きを含む。`apply` は、設定ファイルに
`[[role.policy.ec2]]` が無ければ既定を書く。書かれていれば、それを使う。

`apply` は、`[[role.policy.<ポリシー名>]]` のそれぞれについて、`Effect` の無い
Statement に `Allow` を補い、変数を置き換えた中身と `temt-<ポリシー名>` の今の中身を
比べ、無いか違えば書く。そのあと、設定ファイルに無い `temt-` で始まるインライン
ポリシーを消す。名前を替えて移るときに権限が切れる間を作らないよう、書いてから
消す。報告は `role policy temt-<ポリシー名>:` の行で別に出す。`temt-` で始まらない
インラインポリシーと、管理ポリシーには触れない。

**インスタンスプロファイル `<名前>`。** 上のロールを 1 つだけ入れる。既にあって
ロールが入っていなければ入れる。別のロールが入っていれば、外して入れ替える。

**セキュリティグループ `<名前>`。** 設定ファイルの `SubnetId` が属する VPC に作り、
受信規則を設定ファイルの `[[security-group.ingress]]` に揃える。揃え方、VPC を
変えたときの追従、消し方は [design/security-group.md](design/security-group.md) に
ある。

**起動テンプレート `<名前>-template`。** 設定ファイルと temt が決める項目から
作り、違いがあれば新しいバージョンを作って既定にする。項目とバージョンの扱いは
[design/launch-template.md](design/launch-template.md) にある。

**関連付け `<名前>-sshd`。** インスタンスの sshd の待ち受けポートを設定ファイルの
`SshdPorts` に揃える、State Manager の関連付け。中身、揃え方、起動直後の扱いは
[design/sshd-ports.md](design/sshd-ports.md) にある。

**AMI。** `bake` がサービスのインスタンスから作る。起動テンプレートには設定
ファイルの `ImageId`（AMI の ID か名前）が指す AMI を入れ、無ければ `apply` がその
サービスから焼いた最新のものを選んで名前で書く。他のサービスの AMI も、`ImageId` に
書けば使える。作り方と選び方は [design/ami.md](design/ami.md) にある。

## クライアントのコマンド

クライアントの操作は、すべてコマンド `temt` が行う。Python 3（3.12 以上）の
パッケージ `src/temt/` として書く。リポジトリの `.venv` は `uv sync` が作る開発用で
ある。`deploy` がアプリ ID で指した temt と一緒に配るアプリは、実行に使った `temt` の
パッケージのものになる。`.venv` の `temt` はリポジトリを指すので、リポジトリで
直しているものが送られる。サービスのコマンドと `ProxyCommand` は、`temt` をパスで
なく名前で呼び、そのとき PATH にある `temt` が動く。
AWS の操作は boto3 で行う。`proxy` が Session Manager 経由でつなぐときだけ aws-cli を
呼ぶ。この文書では AWS の API を aws-cli のサブコマンド名（`describe-instances` など）
で書く。boto3 では同じ名前のメソッド（`describe_instances`）になる。

書式は `temt <対象> <動詞> [引数] [コマンドラインオプション]` である。対象は temt が扱う
ものの種類を表す名詞で、動詞がそれへの操作を表す。動詞の後ろの位置引数は、操作する
もの（AMI、インスタンス ID、キーペア名、アプリ ID、ポートなど）を指す。一部のコマンド
には 1 語の短縮形があり、`temt <短縮形> [引数] [コマンドラインオプション]` と打つ。
短縮形は、それが表すコマンドと同じ引数とコマンドラインオプションを取り、同じように
動く。

サービスはコマンドラインオプション `--svc <svc>` で選ぶ。下の表で `--svc <svc>` と
書いたコマンドは `--svc` が要り、`[--svc <svc>]` と書いたコマンド（`service list`、
`instance list`、`ami list`、`ami prune`、`ami delete`、`app list`）は省ける。
`keypair` のコマンドは `--svc` を取らない。`--svc` を付けたコマンドは、そのサービスの
設定ファイルで環境（リージョンとプロファイル）が決まり、扱うものをその
サービスのものに限る。`--svc` を省いたコマンドは、`--profile` と `--region` で
決まる環境の、すべてのサービスのものを扱う。ただし `--svc` を省いた `app list` は、
アプリ ID で指せるアプリだけを扱う。AWS を呼ばないコマンド
（`service list`、`sg list`、`sg add`、`sg remove` と、`--svc` を省いた
`app list`）は `--profile` も `--region` も取らない。コマンドは次のとおり。

この文書と design/ では、短縮形のあるコマンドを短縮形で呼び、`--svc` を省いて書く。

コマンドラインオプションは `temt` より後ろのどこに置いてもよく、それぞれ 1 回まで
受け付ける。値を取るコマンドラインオプション（`--svc`、`--profile`、`--region`、
`--format`、`--user`、`--description`）は、直後の語を値とする。値は空にできない。
ただし `--description` の空の値は説明を消す。それ以外で `-` で始まる語は
コマンドラインオプションとして読み、知らないものは引数の誤りとする。`-` で始まる
位置引数は無い。`app set` の `<キー>=<値>` と `deploy` の `<名前>=<値>` は 1 語の
位置引数で、語の頭が名前なので、値は `-` で始まってもよい。1 文字の
コマンドラインオプションは無い。コマンドラインオプションを除いた語の 1 語めが
対象の名前でも短縮形でもないとき、対象の次の語がその対象の動詞でないときは、
引数の誤りとする。そのコマンドが取らないコマンドラインオプションと、足りない位置
引数、余分な位置引数も、引数の誤りとする。

`--help` があれば、ほかの引数を読まずに使い方を標準出力へ出して終わる。
コマンドラインオプションを除いた語の 1 語めが対象の名前か短縮形で、`--help` が
それより後ろにあれば、その対象（短縮形ならそれが表すコマンドの対象）のコマンドだけの
使い方を出す。そうでなければ、すべてのコマンドの使い方を出す。値を取る
コマンドラインオプションの直後の `--help` は、その値である。

`--version` も同じく、ほかの引数を読まずに `temt <バージョン>` の 1 行を標準出力へ
出して終わる。バージョンは、入れた temt の `pyproject.toml` の `version` である。
`--help` と両方あれば、先にあるほうで終わる。値を取るコマンドラインオプションの
直後の `--version` は、その値である。

`apply` は、サービスのコマンド `~/.local/bin/<名前>` が無ければ書く。`<名前> ...` は
`temt --svc <svc> ...` の別名で、シェルの補完がコマンド名に効くので、サービスの操作は
この形で打てる。`--svc` を省けるコマンドも、サービスのコマンドから呼べば `--svc` を
付けたのと同じである。サービスのコマンドに `--svc` を重ねたときと、サービスの
コマンドで `--svc` を取らない `keypair` のコマンドを呼んだときは、引数の誤りとする。
`temt` は呼ばれた名前を見ない。`proxy` は ssh の ProxyCommand として動き、ssh は
サービスのコマンドを通さず、`temt` を呼ぶ（[design/ssh.md](design/ssh.md)）。

### すべてのコマンドに共通の振る舞い

- `--profile <プロファイル>` を付けると、その実行だけ、設定ファイルの
  `AwsProfile` より優先してそのプロファイルを使う。`apply` はその値を
  `AwsProfile` に書くので、次からのコマンドも同じプロファイルを使う。AWS を呼ばない
  `service list`、`sg list`、`sg add`、`sg remove` と、`--svc` を省いた `app list`
  では引数の誤りとする。
- `--region <リージョン>` は、`service list` と `app list` を除き、`--svc` を省いた
  コマンドだけが受け付ける。`--svc` を付けたときは引数の誤りとする。
- メッセージは標準エラー出力に書く。ProxyCommand として動くとき、標準出力は
  ssh の通信路だからである。進行を知らせる行には時刻を付け、エラーの行には
  プログラム名を付ける。文言は英語で、ASCII 文字だけを使う。ただし、メッセージに
  入れる temt の文言でないもの、つまり利用者の手元から来る値（設定ファイル、ssh の
  設定、環境変数、引数、`manifest.toml` の値、ファイル名やパス、プロファイル名）と、
  AWS や外部コマンドが返した文（botocore の例外の文など）は例外で、日本語などは
  そのまま出す。これらは、誤り、警告、進行を知らせる行の区別なく、表示できない文字
  （制御文字、表示の向きを変える文字、半角スペース以外の空白など）を `?` に置き換えて
  出す。複数行の AWS の誤りの文は、行を `; ` でつないで 1 行にする（`:` で終わる行の
  後ろは空白でつなぐ）。AWS の ID、AMI の名前、状態、規則を通った名前のように、temt や
  AWS が決めた規則に従う値と、OS や Python が返す決まった文（`OSError` の理由など）は
  置き換えない。例外は `manifest.toml` の値とアプリのオプションの値で、メッセージと
  `app show` では、表示できない文字のうち端末を乱すものだけを置き換える（「アプリの
  オプション」）。`list` の表に出すときは、ほかの値と同じく表示できない文字をすべて
  置き換える（「`list` の表」）。`list` の表と `app get` の値と `diff` と `sg diff`
  の差分と `--help` の使い方と `--version` のバージョンだけは標準出力に書く
  （「`list` の表」、「`app` のコマンド」、「`service diff`」、「`sg` のコマンド」）。
- 終了コードは、失敗が 1、引数の誤りが 2 とする。引数の誤りでは、エラーの行に
  続けて使い方を標準エラー出力に書く。コマンドラインオプションを除いた語の 1 語めが
  対象の名前か短縮形ならその対象（短縮形ならそれが表すコマンドの対象）のコマンドだけの
  使い方を、そうでなければすべてのコマンドの使い方を書く。
  Ctrl-C で中断されたときも、その旨を述べて 1 で終わる。
- 使う外部コマンドの有無を、実行前に確かめる。`ssh-keygen` は `apply`、`diff`、
  `keypair` の `show` と `create`、`FINGERPRINT` か `LOCAL` の列を出す `keypair list`
  が使う。
  `proxy` は、`TEMT_LOGIN` が `ssm` なら `aws` と `session-manager-plugin` を使い、
  `direct` なら外部コマンドを使わない。`deploy` と `app remove` は `ssh` を使う。
  無ければ名前を挙げて終了する。boto3 が読み込めなければ、
  AWS を呼ばない `service list`、`sg list`、`sg add`、`sg remove` と、`--svc` を
  省いた `app list` を除き、すべてのコマンドがそれを告げて終了する。
- `bake` が AMI を待つときを除き、待ち合わせには締め切りを置く。段階ごとの締め切りは
  [design/instance.md](design/instance.md#待ち合わせ) にある。締め切りを過ぎたら、
  どの段階が終わらなかったかを述べて終了する。段階が進むたびに 1 回ずつ知らせる。
- `--svc` を付けたコマンドは、設定ファイルが無ければ、`apply` を実行するよう促して
  終了する。`destroy` が要るのは設定ファイルだけで、無ければそれを告げて終了する。
- `apply` 済みを前提とするコマンド（`start`、`bake`、`template show`、`--svc` を
  付けた `app` のコマンド）は、AWS に対する最初の操作の前に起動テンプレートを
  探し、無ければ `apply` を実行するよう促して終了する。`start` は、止めた
  インスタンスを再開するときもテンプレートを確かめる。`apply`、`diff`、`destroy`、`stop`、
  `terminate`、`reboot`、`status`、`instance list`、`ami list`、`ami prune`、
  `ami delete`、`sg diff`、`sg show`、`proxy` は確かめない。`status` は
  止めずに、`apply` されていないことを表示する。`sg show` はセキュリティグループが
  無ければ次の `apply` が作ることを表示し、`diff` は無いリソースを作るものとして、
  `sg diff` はすべての規則を足すものとして出す。
- `start`、`stop`、`terminate`、`reboot` は、既定では完了まで待つ。`--async` を
  付けると、AWS が要求（`run-instances`、`start-instances`、`stop-instances`、
  `terminate-instances`、`reboot-instances`）を受け付けるまでしか待たない。完了とは、
  `start` ではログインできる状態になること（SSM エージェントが、起動より後に
  `Online` と報告する）、`stop` ではインスタンスが `stopped` になること、
  `terminate` ではインスタンスが `terminated` になること、`reboot` では再起動して
  ログインできる状態に戻ること（boot_id が変わったと読める）である。`terminate` は、
  `--async` でも known_hosts を片づける。`bake` と `destroy` はつねに完了を待つ。
- `describe-instances` は要求から数秒遅れるので、`--async` で要求した直後のコマンドは
  古い状態を見ることがある。利用者は、`status` で落ち着いたことを確かめてから次の
  操作をする。確かめずに状態を変えるコマンド（`apply`、`bake`、`deploy` など）を
  打ったときの振る舞いは保証しない。`start`、`stop`、`reboot`、`terminate` は、
  古い状態を見て取り違えても、やり直せば揃うように作る。`start --async` の直後に
  `start` を打つと、2 台目を起動しうる。これは `status` の警告で見えるようにし、
  `terminate` にインスタンス ID を指して片づける。
- `start`、`stop`、`reboot` は、インスタンスが途中の状態でも先回りして断らず、要求を
  そのまま AWS に送る。AWS が断れば、その誤りを見せて終了する。終了の途中のものは、
  `status`、`terminate`、`destroy` のほかでは無いものとして扱い、2 台以上かどうかは
  すべてのコマンドでこれを除いて数える
  （[design/instance.md](design/instance.md#途中の状態)）。
- `apply`、`stop`、`terminate`、`reboot`、`bake`、`destroy`、`ami prune`、
  `ami delete`、`keypair delete` と、`--bake` を付けた `deploy` と `app remove` は、
  変更する前に、対象を挙げて `[y/N]` で確認を求める。`apply` は、違いが無ければ
  確認を求めずに終わる。プロンプトは標準エラー出力に書き、答えは標準入力から
  読む。`y` と答えなければ、何もせずに終了コード 1 で終わる。`--yes` を付ければ
  確認しない。標準入力が端末でなく `--yes` も無ければ、`--yes` が要ると告げて
  終了する。
- `start`、`stop`、`terminate`、`reboot`、`bake`、`destroy`、`deploy`、`app remove`
  は、サービスごとのロックを取ってから動く。`ami prune` は、AMI を 1 つ消すたびに、
  その AMI のサービスのロックを取る
  （[design/instance.md](design/instance.md#ロック)）。

### `list` の表

`service list`、`instance list`、`ami list`、`keypair list`、`app list`、
`sg list` は、docker に倣い、1 行目に列の名前（見出し）を、2 行目から 1 件を
1 行で出す。列は空白で揃え、最後の列は揃えない。見出しは空白を含まない英大文字の
1 語である。値の無いところは `-` と出す。1 件も無ければ見出しだけを出す。改行や
タブなど、表示できない文字は `?` に置き換える。表は UTF-8 で標準出力に書き、
環境の行と警告は標準エラー出力に書くので、表だけを `grep` や `awk` に渡せる。
読み手が途中で閉じれば（`| head` など）、何も言わずに書くのをやめる。どれも
表示するだけで、ロックは取らない。

temt が組み立てる値には、時刻のほかは空白を入れない。時刻は、手元のローカル時刻で
秒までを `2026-09-20 12:00:00` の形で出す（時刻の表示は、表の外も同じ形である）。
起動テンプレートのバージョンは
`<テンプレート名>:<バージョン>` と書き、複数あれば `,` でつなぐ
（`temt-web-template:3,mine:1`）。テンプレート名には `:` も `,` も使えないので、
区切りを取り違えない。AWS や設定ファイルから来る値（AMI の名前、タグの値、
`ImageId` など）は書かれたまま出すので、空白を含みうる。`awk` で列を切り分けるときは、
時刻の列は日付と時刻の 2 つに分かれると見込むか、時刻やそういう列を `--format` で
最後に置く。

`--format <列>[,<列>...]` を付けると、出す列とその順を選べる。
列は見出しの名前で、大文字小文字を問わない。知らない名前、重なった名前、空の名前は、
使える名前を挙げて引数の誤りとする。列には、既定で出すものと、`--format` で選んだ
ときだけ出すものがある。列の名前は、AWS を呼ぶ前に確かめる。選んでいない列のためには
AWS を呼ばない。

### `service apply --svc <svc> [--yes]`（短縮形 `apply`）

サービスの設定ファイル、キーペア、AWS リソース、ssh の設定を、無ければ作る。既に
あるものは、キーペア以外は設定ファイルに合わせ、キーペアは変えない。何度
実行しても同じ結果になる。各手順は、設定ファイルを正として対象の 1 つを揃える
独立した処理とする。

`apply` は、検出、表示、確認、更新の順に動く。

- **検出**: 下の手順 1〜7 をたどり、対象ごとに差分を検出する。差分の検出は `diff`
  と同じ処理である。この間は、設定ファイルにも AWS にも手元のファイルにも書かない。
  手順の中で止まれば、何も書かずに終了する。
- **表示**: 違いが無ければ、そう知らせて終わる。違いがあれば、`diff` と同じ形で標準
  エラー出力に表示する。
- **確認**: `[y/N]` で確認を求める（「すべてのコマンドに共通の振る舞い」）。
- **更新**: 手順の順に、検出した差分で更新する。作ったもの、更新したもの、消した
  ものを知らせる。変えなかったものは知らせない。検出してから更新するまでの間に AWS の
  状態が変わることは扱わない。

途中で失敗しても、同じコマンドをもう一度実行すれば続きから進む。更新の途中で
止まれば、そこまでに書いたものは残る。

1. サービス名を「名前」の規則で検査する。ssh ディレクトリの `config` にある
   `Host <名前>` のブロックが別の conf ディレクトリから `apply` したもので、その
   場所にこのサービスの設定ファイルがまだあれば（今の場所のファイルと実体が同じ
   なら除く）、その場所を挙げて終了する
   （[design/ssh.md](design/ssh.md#conf-ディレクトリをまたぐサービス)）。
2. 設定ファイルを読む（無ければ既定だけで始める）。書かれていないか値の違う項目を、
   値を決めながら検出する。書かれていない `ImageId` と `SubnetId` は、ここで AWS から
   選ぶ。`[[role.policy.ec2]]` が無ければ、既定を足すことにし、足せるかを確かめる
   （[conf.md](conf.md#role)）。検出した値は、後の手順が書いたものとして使う。
   更新では、`--profile` の `AwsProfile` を先頭に、conf.md の表の順に項目を書き、
   次に `[[role.policy.ec2]]` の既定を足す。ファイルを新しく作ったときは、最後に
   書き方の例をコメントで足す。
3. ssh ディレクトリと `keys/` と、その無い親ディレクトリを、作るかモード 700 に
   締めることを検出する。サービスのコマンド `~/.local/bin/<名前>` が無ければ、書く
   ことを検出する。何かあれば、中身にかかわらず触れない。行き先の無いシンボリック
   リンクも、あるとみなす。更新で書くときは、`~/.local/bin` が無ければ作る。PATH に
   `temt` があるかは確かめない。無ければ、ssh を打ったときに気づける。
4. `SubnetId` のサブネットが存在し IPv4 の CIDR を持つことを確かめ、VPC と IPv6 の
   CIDR の有無を得る。サブネットが無ければ、別のアカウントで作るなら `SubnetId` と
   `ImageId` の行を消すよう添える。続いて `ImageId` が指す AMI が使える状態で
   あることを確かめ、名前で書かれていれば ID を引く
   （[design/ami.md](design/ami.md#名前で指す)）。無いか使えなければ、`ImageId` の
   行を消して選び直すよう添える。`VolumeSize` が書かれていれば、その AMI の
   ルートボリューム（`BlockDeviceMappings` のうち `DeviceName` が `RootDeviceName`
   のもの）の大きさと比べ、`VolumeSize` の方が小さければ、両方の大きさを挙げて
   止まる。AWS は小さい値を起動テンプレートには受け付け、起動するときに断るから
   である。AMI に EBS のルートボリュームが無ければ（大きさが分からなければ）、
   `VolumeSize` の行を消すよう告げて止まる。`[[role.policy.<ポリシー名>]]` のそれぞれについて、`Effect` を補い、
   変数を置き換えて `temt-<ポリシー名>` の中身を作り、IAM Access Analyzer の
   `ValidatePolicy` にかける。`ERROR` の指摘があれば、すべて挙げる
   （[conf.md](conf.md#role)）。
5. キーペアと手元の鍵を [design/keypair.md](design/keypair.md) のとおりに比べる。
   鍵が一致しなければ、設定ファイルの誤りとして終了する。
6. IAM ロール、そのインラインポリシー `temt-<ポリシー名>`、
   インスタンスプロファイル、セキュリティグループ、起動テンプレート、
   関連付けの差分を、この順に検出し、更新でもこの順に揃える。消すのは、設定
   ファイルに無い `temt-` で始まるインラインポリシーである。インスタンス
   プロファイルに別のロールが入っていれば、外してロール `<名前>` を入れる。
   セキュリティグループをまだ作っていなければ、起動テンプレートの差分は、その ID を
   `(new)` として検出し、更新では作ったセキュリティグループの ID を入れる。関連付けは
   名前で探し、作ったときと中身を更新したときだけ、実行を求める
   （[design/sshd-ports.md](design/sshd-ports.md)）。インスタンスプロファイルを
   作った直後は、boto3 の waiter（状態が変わるまで問い合わせを繰り返す仕組み）
   `instance-profile-exists` で IAM の反映を待つ。それでも直後の `start` が
   インスタンスプロファイルの不在で失敗することがあり、その場合は `start` をもう
   一度実行すればよい。
7. ssh ディレクトリの `config` の `Host <名前>` ブロックを、設定ファイルに合わせて
   足すか更新することを検出する。`~/.ssh/config` の目印の次の行を、その `config` を
   指す `Include` にすることを検出する。張り替えるときは、前の `Include` が指して
   いたファイルの Host のうち、ssh から見えなくなるものを、更新で警告する
   （[design/ssh.md](design/ssh.md)）。どちらのファイルも、更新で書く前に読み直し、
   検出したときから中身が変わっていれば、書かずに止まる。読み直してから書き終える
   までは、ssh ディレクトリの `.config.lock` に排他ロックを掛ける。ロックは
   ssh ディレクトリごとに 1 つでサービスによらず、持っているものがあれば離すまで
   待つ。別のサービスの `apply` が同時に書いても、片方の書き換えを消さない。
   `TEMT_SSH_DIR` を変えて同時に打った `apply` どうしは、`~/.ssh/config` の
   書き換えで守り合わない。

### `service diff --svc <svc>`（短縮形 `diff`）

次の `apply` が何を変えるかを、1 つの変更を 1 行で標準出力に書く。`apply` の手順を
同じ順にたどり、差分を検出するだけで、設定ファイルにも AWS にも手元のファイルにも
書き込まない。ロックは取らず、確認も求めない。設定ファイルが無ければ、`apply` を
実行するよう促して終了する。起動テンプレートの有無は確かめない。

手順 2 は書かずに、書く項目を出し、決まった値をその後の手順で使う。`--profile` を
付ければ、`AwsProfile` に書く値も出す。`apply` が止まるところでは、それまでに検出した
変更を出してから、同じエラーで終わる。出すものは次のとおり。

| 手順 | 種類 | 名前 | 出すもの |
| --- | --- | --- | --- |
| 2 | `conf` | 項目の位置（`launch-template.ImageId` など） | 書く値。書かれていれば `<今の値> -> <新しい値>` |
| 2 | `conf` | `role.policy.ec2` | 既定を書くこと |
| 3 | `dir` | ssh ディレクトリと `keys/`、その無い親ディレクトリ | 作ること、モードを 700 にすること |
| 3 | `command` | サービスのコマンド | 書くこと |
| 5 | `key` | `IdentityFile` | 鍵を作ること（無い親ディレクトリも作る） |
| 5 | `keypair` | `<KeyName>` | 登録すること |
| 6 | `role` | `<名前>` | 作ること、足すタグ |
| 6 | `role-policy` | `temt-<ポリシー名>` | 足すこと、書き換えること、消すこと。中身の違い |
| 6 | `instance-profile` | `<名前>` | 作ること、足すタグ、入れるロール（別のロールが入っていれば、それとの入れ替え） |
| 6 | `security-group` | `<名前>` | 作ること、足すタグ |
| 6 | `ingress` | `PORT` | 足す規則、説明を直す規則、消す規則 |
| 6 | `launch-template` | `<名前>-template` | 作ること、項目ごとの違い、足すタグ、消す既定以外のバージョン |
| 6 | `association` | `<名前>-sshd` | 作ること、ドキュメント、対象、`SshdPorts`、スクリプトの違い、足すタグ |
| 7 | `ssh-host` | `<名前>` | Host ブロックを足すこと、書き換えること。中身の違い |
| 7 | `ssh-include` | `~/.ssh/config` | `Include` の行を足すこと、張り替えること（`~/.ssh` が無ければ作る） |

行は、頭の印、種類、名前、違いを、空白で揃えて並べる。頭の印は `+`（作る、足す）、
`~`（直す）、`-`（消す）のどれかである。
値が変わるものは、違いを `<今の値> -> <新しい値>` と書く。足すタグは
`tags: <キー>=<値>` と書く。受信規則は、名前に `PORT` を、違いに送信元と説明を
`sg diff` と同じ形で書く。起動テンプレートは、temt が管理する項目のうち違うものを
1 つ 1 行で出す。その中で、まだ作っていないセキュリティグループの ID は `(new)` と
書く。`BlockDeviceMappings` は、設定ファイルの項目名 `VolumeSize` で大きさだけを
出し、入っていなければ `-` と書く（`VolumeSize: - -> 30`）。項目ごとに開いても
違いが見えないときは `new version` と書く。新しいバージョンを作らないときに、既定
以外のバージョンが残っていれば、それを消すことを `delete other versions: <番号>, ...`
と書く。インラインポリシーの中身（キーを並べ替えて字下げした JSON）、関連付けのスクリプト、Host ブロックは、違いを
unified diff の形（前後の行を添え、消す行に `-`、足す行に `+` を付ける）で、続く
行に字下げして出す。`Include` を張り替えると ssh から見えなくなる Host があれば、
続く行に挙げる。

並べる順は `apply` の手順の順で、受信規則は `sg diff` と同じ順である。違いが
無ければ、標準出力には何も書かず、その旨を標準エラー出力に知らせる。終了コードは、
違いの有無によらず 0 とする。関連付けの実行の要求は、定義の変更ではないので出さない。
例:

```
~   role-policy       temt-app
    @@ -2,5 +2,8 @@
       "Statement": [
         {
    -      "Action": "s3:GetObject",
    +      "Action": [
    +        "s3:GetObject",
    +        "s3:PutObject"
    +      ],
           "Effect": "Allow",
           "Resource": "arn:aws:s3:::web-data/*"
+   ingress           443/tcp             0.0.0.0/0   https
~   launch-template   temt-web-template   InstanceType: t3.micro -> t3.small
~   association       temt-web-sshd       SshdPorts: 22 -> 22,2222
    @@ -1,4 +1,4 @@
     set -u
    -want="22"
    +want="22 2222"
     svc="web"
     conf=/etc/ssh/sshd_config.d/temt-sshd-ports.conf
```

### `instance start --svc <svc> [--async]`（短縮形 `start`）

1. ロックを取り、起動テンプレートがあることを確かめる。ロックの後で、サービスの
   インスタンスを探す（[design/instance.md](design/instance.md#探す)）。終了の途中
   （`shutting-down`）のものは、無いものとして扱う
   （[design/instance.md](design/instance.md#途中の状態)）。
2. 見つかった数と状態で分ける。
   - 2 台以上: それらを列挙し、余分なものをインスタンス ID を指して `terminate` で
     終了するよう告げて終了する。
   - `running`、`pending`: 起動しない。3 へ進む。
   - `stopped`、`stopping`: `start-instances` で再開を求め、そう知らせる。停止の途中
     でも、止まるのを待たない。起動テンプレートは使わないので、止めた後に `apply` で
     変えた起動テンプレートの中身（AMI、インスタンスタイプなど）は効かない。
   - 無し: `<名前>-template` の既定バージョンから `run-instances` で起動する。
3. `--async` が付いていればここで終わる。付いていなければ、再開を求めたときは、
   古い状態が見えなくなるまで待つ
   （[design/instance.md](design/instance.md#前の状態が見えなくなるまで)）。続けて
   `running` になるまで待つ。起動した直後で、ID で引いても見えないあいだも待つ。
   続けて SSM エージェントが `Online` と報告されるまで
   `ssm describe-instance-information` を繰り返し、ログインできる状態になったと
   知らせて終わる。`Online` は、最後の応答（`LastPingDateTime`）がインスタンスの
   起動時刻（`LaunchTime`。再開すると再開した時刻になる）より後のものだけを
   数える。停止してすぐ再開すると、止まる前の `Online` の報告が残っていることが
   ある。

`--async` は、AWS が `run-instances` か `start-instances` を受け付けるまでしか
待たない。インスタンスが `pending` のうちに ssh でつなげば、`proxy` がつなげるように
なるまで待つ。ただし、`describe-instances` は要求から数秒遅れるので、要求した直後は、
起動したインスタンスがまだ見えないか、再開を求めたインスタンスが `stopped` の
ままに見えることがある。そのとき `proxy` は、インスタンスが無い、または止まって
いると告げて終わる。`start` し直すと 2 台目を起動しうるので
（[design/instance.md](design/instance.md#探す)）、`status` を見てからつなぎ直す。

### `instance stop --svc <svc> [--async] [--yes]`（短縮形 `stop`）

インスタンスを終了せずに停止する。ディスクの中身、インスタンス ID、ホスト鍵は
残るので、known_hosts には触れない。止めたインスタンスは、次の `start` が再開する。
起動テンプレートの有無は確かめない。

1. ロックを取り、`start` と同じ条件でインスタンスを探し、`start` と同じく終了の
   途中のものを除く。
   - 無し: 無いと知らせて終わる。エラーにはしない。
   - 2 台以上: `start` と同じく、列挙して終了する。
2. 見つかったインスタンスの状態で分ける。
   - `stopped`: 既に止まっていると知らせて終わる。
   - `stopping`: 停止を求めず、確認もせずに 4 へ進む。
   - `running`、`pending`: 3 へ進む。起動の途中でも、動き出すのを待たない。
3. インスタンスの ID と状態を挙げて確認し、`stop-instances` で停止を求め、そう
   知らせる。
4. `--async` が付いていればここで終わる。付いていなければ、`stopped` になるまで
   待つ。古い `running` が見えても、待ち続ける。締め切りを過ぎたら、`status` を
   見るよう添え、インスタンスの中の `systemd-inhibit` のロックが停止を遅らせうる
   ことも添える。

### `instance terminate --svc <svc> [<インスタンスID>...] [--async] [--yes]`（短縮形 `terminate`）

インスタンス ID は、`i-` と 8 桁か 17 桁の小文字の 16 進数である。形が違えば引数の
誤りとする。同じ ID を 2 度書いたときも、引数の誤りとする。

1. ロックを取り、`start` と同じ条件でインスタンスを探す。終了の途中のものも含める。
2. 終了するものを選ぶ。
   - ID を省いたとき: 見つかったものすべてを選ぶ。見つからなければ、無いと知らせて
     終わる。エラーにはしない。
   - ID を指したとき: 指したものを選ぶ。指した ID が見つかったものに無ければ、
     見つかったものを挙げ、何もせずに終了する。
3. 選んだインスタンスの ID と状態を挙げて確認する。その前に、選んだ
   インスタンスに入れてまだ焼いていないアプリ（`deploy` の記録の `instance` が
   その ID のもの）があれば、終了すると消えることを警告する。記録が読めなければ
   警告して続ける。
4. 選んだインスタンスのそれぞれを終了し、その known_hosts を消す
   （[design/instance.md](design/instance.md#終了する)）。2 台以上あってもすべてに
   行う。
5. `--async` が付いていればここで終わる。付いていなければ、選んだすべての
   インスタンスが `terminated` になるまで待つ。状態が変わるたびに知らせる。

### `instance reboot --svc <svc> [--async] [--yes]`（短縮形 `reboot`）

インスタンスを終了せずに再起動する。ディスクの中身、インスタンス ID、ホスト鍵は
変わらないので、known_hosts には触れない。起動テンプレートの有無は確かめない。

`reboot-instances` の後もインスタンスは `running` のままで、SSM エージェントの
`Online` の報告は落ちてからもしばらく残る。どちらでも再起動の前と後を見分けられない
ので、インスタンスの boot_id（`/proc/sys/kernel/random/boot_id`。起動のたびに変わる
ID）を Run Command（`send-command` で `AWS-RunShellScript` を実行する）で読み、
再起動の前と比べる。

1. ロックを取り、`start` と同じ条件でインスタンスを探し、`start` と同じく終了の
   途中のものを除く。
   - 無し: `start` するよう告げて終了する。
   - 2 台以上: `start` と同じく、列挙して終了する。
   - `stopped`: `start` するよう告げて終了する。
   - `running`、`pending`、`stopping`: 2 へ進む。途中の状態でも、終わるのを
     待たない。
2. `--async` が付いていなければ、SSM エージェントが `Online` かを確かめる。
   `Online` でなければ再起動の終わりを見分けられないので、`--async` を付けて
   やり直すよう告げて終了する。AWS に断られたときは、その誤りだけを出す。
   `--async` なら SSM は使わない。
3. インスタンスの ID と状態を挙げて確認する。
4. `--async` が付いていなければ、再起動の前の boot_id を読む。締め切りまでに
   読めなければ、`--async` を試すよう添えて終了する。AWS に断られたときは、その
   誤りだけを出す。どちらでも、再起動はまだ求めていない。2 とここでは、インスタンスの
   状態によらず、`--async` を試すよう添える。
5. `reboot-instances` で再起動を求め、そう知らせる。
6. `--async` が付いていればここで終わる。
7. boot_id が 4 と違うと読めるまで待ち、ログインできると知らせて終わる。Run Command
   は、SSM エージェントが再起動を求めた時刻（`reboot-instances` の応答の時刻）より
   後に `Online` と報告してから送る。再起動の間も `Online` の報告は残り、エージェント
   は起動するとすぐ報告するので、落ちる前のエージェントに送って再起動に巻き込まれる
   ことを避けられる。そう報告するまでの間は、インスタンスの状態も見て、`running` を
   待つときと同じ状態（[design/instance.md](design/instance.md#待ち合わせ)）に
   なれば、締め切りを待たずにその状態を述べて終了する。締め切りを過ぎたら、
   `status` を見るよう添えて終了する。エージェントの戻りを待ち始めたとき、戻って
   boot_id を読み始めたとき、前の boot_id が返ってきたときに、それぞれ 1 回ずつ
   知らせる。

boot_id は、問い合わせのたびに次のように読む。4 と 7 で同じである。

- 送った Run Command が無ければ、SSM エージェントが `Online` と報告しているときに
  限り、1 つ送る。`send-command` が `InvalidInstanceId`（エージェントが受け取れ
  ない）で断られたら、送れなかったものとして次の問い合わせで送り直す。
- 送ったものがあれば、その結果を `get-command-invocation` で見る。実行の記録が
  まだ無い（`InvocationDoesNotExist`）ときと、`InvalidInstanceId` で断られたときは、
  まだ終わっていないものとする。`Success` で標準出力が空でなければ、それを
  boot_id とする。それ以外で終わったとき（`Success` でも標準出力が空のときを
  含む）と、送ってから 1 分たっても終わらないときは、見切って次の問い合わせで
  送り直す。
- 受け取りの締め切り（`TimeoutSeconds`）とインスタンスの中での実行の締め切り
  （`executionTimeout`）は、どちらも 30 秒とする。コマンドは 2 つの和の 60 秒で
  打ち切られるはずだが、再起動に巻き込まれたものは終わったという報告が遅れる
  ことがあるので、1 分で見切る。
- 7 では、落ちる直前に報告したエージェントが古い boot_id を返すことがある。古ければ、
  次の問い合わせで送り直す。

手元の資格情報には、`ssm:SendCommand` と `ssm:GetCommandInvocation` の権限が要る。
インスタンスのロールの `temt-ec2` の既定（[conf.md](conf.md#role)）に、Run Command
の実行に要る権限が入っている。

### `ami bake --svc <svc> [--yes]`（短縮形 `bake`）

インスタンスを停止して AMI にし、設定ファイルの `ImageId` と起動テンプレートを
新しい AMI に向け、インスタンスを終了する。インスタンスの中には手を加えない。
古い AMI は消さず、他のサービスの設定ファイルとテンプレートには触れない。
`--async` は無く、つねに完了を待つ。AMI の名前とタグは
[design/ami.md](design/ami.md) にある。

1. ロックを取り、起動テンプレートがあることを確かめ、`start` と同じ条件で
   インスタンスを探す。
2. 見つかった数と状態で分ける。
   - 無し: 焼くインスタンスが無いと告げ、エラーにして終了する。
   - 2 台以上: `start` と同じく、列挙して終了する。
   - `pending`、`stopping`: 終わるのを待ってやり直すよう告げて
     終了する。
   - `running`、`stopped`: 3 へ進む。
3. 起動テンプレートの既定バージョンを、設定ファイルから来る 5 つの項目で設定
   ファイルと比べる。`ImageId` は指す AMI の ID を引いてから比べ、使える AMI が
   無ければ違う項目とする。`VolumeSize` は、書かれていなければテンプレートに
   `BlockDeviceMappings` が無いことを、書かれていれば大きさが同じことを比べる。
   違う項目か、`VolumeSize` を除いて書かれていない項目があれば、先に `apply` を
   実行するよう告げて終了する。続けて、`VolumeSize` が書かれていれば、インスタンスの
   ルートボリューム（`BlockDeviceMappings` のうち `DeviceName` が `RootDeviceName`
   のものの `VolumeId` を `describe-volumes` で引いたもの）の大きさと比べる。
   インスタンスの方が大きければ、焼かずに終了する。`VolumeSize` をその大きさ以上に
   直すか、行を消すかしたうえで、どちらも `apply` してから焼くよう告げる。そのまま
   焼くと、AMI が `VolumeSize` より大きくなり、次の `start` を AWS が断るからである。
4. インスタンスの ID と状態を挙げ、`running` なら停止すること、AMI を作ること、
   AMI が使えるようになったら設定ファイルの `ImageId` を書き換えること、
   インスタンスを終了することを示して確認する。
5. `running` なら `stop-instances` で停止し、`stopped` になるまで待つ。
6. `create-image` で AMI を作り、その ID と名前を知らせる。
7. AMI が `available` になるまで待つ。締め切りは置かない。AMI の大きさによっては
   長くかかり、待ち切れずに止めても、まだ何も変えていないからである。作れなかったら
   （[design/instance.md](design/instance.md#待ち合わせ)）、AWS が返した理由
   （`StateReason` の `Message`）を添えてエラーにして終了する。待つあいだに AWS の
   誤り（資格情報の期限切れなど）が出たときも、その誤りで終了する。どちらも、
   エラーの前に今の状態を知らせる。設定ファイル、テンプレート、記録は変えていない
   こと、インスタンスが停止したまま残っていること、AWS の誤りなら AMI がまだ
   `available` でないことである。次に何をするかの案内は出さない。
8. 設定ファイルを読み直し、`ImageId` を新しい AMI の名前に書き換え、元の値と
   新しい名前を知らせる。ファイルが無ければ作らずにエラーにする。
   起動テンプレートには、既定バージョンの内容の `ImageId` だけを替えた新しい
   バージョンを作って既定にし、他のバージョンを消す
   （[design/launch-template.md](design/launch-template.md#バージョン)）。
   続けて、`deploy` の記録（[`app` のコマンド](#app-のコマンド)）も新しい AMI に
   向け、記録が持つ AMI がテンプレートと食い違わないようにする。書き換えるのは次の
   2 つで、`instance` を消したものだけを焼いたと知らせる。記録が読めないか書けなければ、
   警告して続ける。形が違って読めない `options` と `baked_options` は、書かれていた
   ままの値で書き戻す。
   - `instance` がこのインスタンスの記録: `version` を `baked_version` に、新しい
     AMI の ID を `baked_image` に、`options` を `baked_options` に書き、`instance` を
     消す。`options` が読めなければ、書かれていたままの値を `baked_options` に写し、
     `--reset` を付けて `deploy` し直すよう警告する。
   - `baked_image` がこのインスタンスの起動元の AMI の記録: `baked_image` だけを
     新しい AMI の ID にする。起動元の AMI に焼いてあった版は、このインスタンスにも
     入っていて、新しい AMI に引き継がれるからである。
9. `terminate` の手順 4 を行い、インスタンスが `terminated` になるまで待つ。

AMI が使えるようになるまで何も向けないのは、作れなかったときや待つあいだに止めた
ときに、何も変わらないようにするためである。直し方は「原因を直して `bake` を
やり直す」だけになる。作れない原因は、AWS の一時的な誤りのほか、暗号化した
EBS の KMS の鍵が使えないなど、利用者が直すものもある。直さずにやり直しても
同じなので、AWS の理由を見せる。作れなくてもインスタンスは停止したまま残り、
`start` はテンプレートを使わずにそれを再開するので、サービスは使い続けられる。

引き換えに、AMI が `available` になってからテンプレートを向けるまでの短い間、新しい
AMI はどのテンプレートからも指されない。同じマシンの `ami prune` は、消す前に
サービスのロックを取るので、この間の AMI を消さない（`ami prune` の節）。

途中で止まったとき（中断、締め切り、AWS のエラー）は次のようになる。

- 6 で AMI ができる前: インスタンスが停止していることがある。6 の最中に中断した
  ときは、`temt:service` タグの付いた AMI ができていることがある。もう一度 `bake` を
  実行する。
- 6 の後、8 で設定ファイルを書き換える前（7 で待つあいだの中断を含む）: 何も
  変わらず、インスタンスは停止したまま残る。知らせた AMI が後で `available` に
  なったら（`ami list` で分かる）、もう一度 `bake` を実行する。AMI がもう 1 つ
  できるが、余分な方は `ami prune` が消す。または、その AMI の名前を `ImageId` に
  書いて `apply` を実行し、`terminate` を実行する。こちらは記録が焼いていないままに
  なるので、`app list` で `lost` と出る。`deploy` し直して焼けば揃う。
- 8 で設定ファイルを書き換えた後、テンプレートを向ける前: 設定ファイルは新しい
  AMI を指し、記録は焼いていないままである。`apply` を実行してから、もう一度
  `bake` を実行する（記録も揃う）か、`terminate` を実行する（`app list` で `lost` と
  出る。`deploy` し直して焼けば揃う）。
- 8 でテンプレートを向けた後、記録を書き換える前: 記録は焼いていないままになり、
  記録の AMI とテンプレートの AMI が食い違って、`app list` で `lost` と出る。アプリは
  AMI に入っているので、`deploy` し直して焼けば揃う。`terminate` を実行する。
- 9: `terminate` を実行する。

テンプレートを向ける前に止まったときは、新しい AMI はどのテンプレートからも
指されていないので、`ami prune` を打つと消える。設定ファイルの `ImageId` がその
AMI を指すとき（8 で書き換えた後に止まったときと、自分で書いたとき）は、
`ami prune` より先に `apply` を実行する。設定ファイルを書き換える前に止まり、
もう一度 `bake` するなら、消えても困らない。

### `ami list [--svc <svc>] [--format <列>]`

temt の AMI を、1 つ 1 行の表で挙げる。temt の AMI とは、自分のアカウントにあって
`temt:service` タグを持つ AMI である。`--svc` を付ければ、そのサービスの設定
ファイルで環境が決まり、`temt:service=<svc>` の AMI だけを挙げる。省けば、
`--profile` と `--region` で決まる環境の、すべての temt の AMI を挙げる。

| 列 | 既定で出す | 値 |
| --- | --- | --- |
| `ID` | 出す | AMI の ID |
| `NAME` | 出す | AMI の名前 |
| `STATE` | 出す | 状態 |
| `CREATED` | 出す | 作成日時 |
| `USED` | 出す | その AMI を指す起動テンプレートのバージョン |
| `SERVICE` | | `temt:service` の値 |

`USED` のテンプレートは、temt のものに限らず、その
アカウントとリージョンにあるすべてのテンプレートのすべてのバージョンを見る。
`ImageId` が SSM パラメータ（`resolve:ssm:`）のバージョンは、AWS に解決させ
（`ResolveAlias`）、今指している AMI の参照とする。解決できなければ、そのバージョンを
挙げて警告する。`ami prune` の候補（`bake` が作った名前で、状態が `available` か
`failed` のもの）のうち `USED` が `-` のものを、`ami prune` は消す。並べる順は、
`temt:service` の値、作成日時の順である。登録を解除した直後に見える `deregistered`
の AMI と、`describe-images` が既定では返さない `disabled` の AMI は出さない。

### `ami prune [--svc <svc>] [--yes]`

どの起動テンプレートのどのバージョンからも指されていない temt の AMI の登録を解除し、
スナップショットも消す。環境と、扱う AMI の範囲は `ami list` と同じく、`--svc` を
付ければそのサービスの設定ファイルで環境が決まり、`temt:service=<svc>` の AMI だけを
扱う。省けば、`--profile` と `--region` で決まる環境の、すべての temt の AMI を扱う。
始める前にはロックを取らず、4 で AMI を 1 つ消すたびに、その AMI のサービスの
ロックを取る。ロックの場所を決める `TEMT_SSH_DIR` の値は、確認の後で止まらない
よう、始める前に確かめる。

1. `ami list` と同じく temt の AMI を集め、候補を絞る。候補は、名前が
   `temt-<temt:service の値>-<YYMMDDHHMM>` の形（`bake` が作った名前）で、状態が
   `available` か `failed` のものである。`pending` は `bake` の途中なので除く。
2. `ami list` と同じくテンプレートのすべてのバージョンを見て、指されている候補を
   残し、残りを消す。`--svc` を付けても、見るのは環境のすべてのテンプレートである。
   サービスごとの最新も、インスタンスが起動に使った AMI も、手元の
   設定ファイルの `ImageId` が指す AMI も、残す理由にしない。どの AMI を指すか
   解決できないバージョンがあれば、それを挙げて、何も消さずにエラーにする。AMI を
   テンプレートより先に集めるのは、テンプレートを読んだ後で `available` になり、
   `bake` がテンプレートを向けた AMI を、候補にしないためである。
3. 消すものが無ければそう告げて終わる。あれば、消すものだけを挙げて 1 度だけ
   確認する。指されていて残す AMI は挙げない（確かめるには `ami list` を使う）。
4. 消すものを 1 つずつ、次の順に扱う。残したものは、理由を添えて警告して残りを
   続け、最後に、残したものをまとめて挙げてエラーにする。
   1. その AMI の `temt:service` の値のサービスのロックを取る。他のコマンドが
      持っていれば、取れないので残す。このマシンにそのサービスの known_hosts の
      ディレクトリ（ロックのファイルを置く場所）が無ければ、このマシンではその
      サービスのコマンドが動いていないので、ロックを取らずに進める。ディレクトリは
      作らない。他のマシンで焼いたサービスのディレクトリを増やさないためである。
      値がサービス名の規則に合わないときも、temt のコマンドがそのサービスを
      扱えないので、ロックを取らずに進める。
   2. 手順 2 と同じくテンプレートのすべてのバージョンを読み直す。その AMI を指す
      バージョンか、どの AMI を指すか解決できないバージョンがあれば、残す。確認を
      待つあいだに、`bake` がテンプレートを向けたかもしれないからである。
   3. `deregister-image` に `DeleteAssociatedSnapshots` を付けて登録解除する。AWS に
      断られたら残す。接続の失敗などで AWS の答えが得られなければ、そこで止める。
      消せなかったスナップショットは、AWS が返した理由を添えて警告する。
   4. ロックを離す。

登録を解除しても、動いているインスタンスと `stopped` のインスタンスには影響しない。
`destroy` のあとに打てば、そのサービスのテンプレートが消えているので、その
サービスの AMI は、他のテンプレートが指していない限り消える。設定ファイルの
`ImageId` は消えた AMI を指したまま残るので、次の `apply` は行を消すよう告げて止まり、
消せば Ubuntu 24.04 から作り直す。

並行する `bake` の新しい AMI は、待っているあいだは `pending` なので候補にならない。
`available` になってから `bake` がテンプレートを向けるまでの短い間は、どの
テンプレートからも指されないが、`bake` はその間もロックを持っているので、同じマシン
から打った `ami prune` はその AMI を消さない。ロックを取れずに残すか、`bake` が
テンプレートを向けてロックを離した後で取り、読み直したテンプレートが指している
ので残す（手順 4）。

### `ami delete [--svc <svc>] <AMI の ID または名前> [--force] [--yes]`

ID か名前で指した temt の AMI 1 つの登録を解除し、スナップショットも消す。環境は
`ami prune` と同じく、`--svc` を付ければそのサービスの設定ファイルで、省けば
`--profile` と `--region` で決まる。サービスごとのロックは取らない。

1. AMI を探す。ID か名前かの見分け方と、名前の探し方は `ImageId` の値と
   同じである（[design/ami.md](design/ami.md#名前で指す)）。ただし ID でも、
   自分のアカウントの AMI からだけ探す（`Owners=self`）。見つからなければ
   エラーにする。`ami list` と同じく、`disabled` の AMI は見えないので扱わない。
   `--svc` を付けたときは、`temt:service` の値が `<svc>` でない AMI（タグの
   無いものを含む）を、見つからないものとしてエラーにする。省いたときは、
   `temt:service` タグの無い AMI をエラーにする。`--force` でもこれらは
   変わらない。名前が `bake` の作った形かは問わない。
2. `ami list` と同じくテンプレートのすべてのバージョンを見る。次のどれかに当たれば、
   `--force` が無ければ理由を挙げて、何も消さずにエラーにする。`--force` があれば、
   理由を警告として挙げて続ける。
   - その AMI を指すバージョンがある。
   - どの AMI を指すか解決できないバージョンがある。
   - 状態が `pending` である。

   `ami prune` と同じく、インスタンスが起動に使った AMI も、手元の設定ファイルの
   `ImageId` が指す AMI も、理由にしない。
3. 消す AMI を挙げて確認する。
4. `deregister-image` に `DeleteAssociatedSnapshots` を付けて登録解除する。AWS に
   断られたらエラーにする。消せなかったスナップショットは、AWS が返した理由を添えて
   警告する。

`--force` で、テンプレートが指している AMI を消すと、そのバージョンからは起動でき
なくなる。既定のバージョンが指していれば、次の `start` は失敗する。`--force` の
有無にかかわらず、設定ファイルの `ImageId` が消した AMI を指していれば、次の
`apply` は行を消すよう告げて止まる。

### `service destroy --svc <svc> [--yes]`（短縮形 `destroy`）

インスタンスを終了し、`apply` が作った AWS リソースとサービスのコマンドを消す。
設定ファイル、鍵、`~/.ssh/temt/config` の Host ブロック、キーペア、AMI は
残し、次の `apply` がそのまま使う。`--async` は無く、つねに完了を待つ。

1. ロックを取り、`start` と同じ条件でインスタンスを探す。終了の途中のものも含める。
2. 見つかったインスタンスの ID と状態、消すリソースの名前（関連付けを含む）を
   挙げて確認する。ロールにはインラインポリシーの名前を添える。
3. インスタンスがあれば、`terminate` の 4 を行い、すべてが `terminated` になるまで
   待つ。
4. 起動テンプレート、関連付け、SSM パラメータ、セキュリティグループ、インスタンス
   プロファイル、IAM ロールを、この順に消す。消したもの、既に無かったものを、
   それぞれ知らせる。
   - 関連付けは、名前が `<名前>-sshd` のものをすべて消す。
   - SSM パラメータは、`/<名前>` の階層の下にあるものをすべて消す。タグではなく
     パスで探す。
   - セキュリティグループは、名前が `<名前>` のものを VPC を問わずすべて消す
     （[design/security-group.md](design/security-group.md#消す)）。
   - インスタンスプロファイルからはロール `<名前>` だけを外す。ロールからは、
     インラインポリシーを持ち主を問わずすべて消す。
   - ロールに管理ポリシーか、他のインスタンスプロファイルが付いていれば、
     インラインポリシーも消さずに止める。先に消すと、ロールが残るのに手で付けた
     ポリシーだけが失われるからである。
5. `~/.ssh/temt/known_hosts.d/<名前>/` と、サービスのコマンド `~/.local/bin/<名前>` を
   消す。サービスのコマンドは、中身にかかわらず消す。
6. 残したものを知らせる。キーペア `<KeyName>` と手元の鍵、設定ファイル、Host
   ブロック、`temt:service=<svc>` の最新の AMI（あれば）。

途中で失敗しても、同じコマンドをもう一度実行すれば続きから進む。

### `service list [--svc <svc>] [--format <列>]`

手元の設定ファイルを、1 つ 1 サービスとして、サービス名の順に表で並べる。AWS は
呼ばない。AWS 側の状態は、インスタンスなら `instance list`、起動テンプレートなら
`template show` で見る。`--profile` と `--region` は引数の誤りとする。

`--svc` を付ければ、そのサービスの設定ファイルだけを読み、1 行を出す。無ければ
`apply` を実行するよう促し、読めなければ理由を告げて、終了コード 1 で終わる。

`--svc` を省けば、conf ディレクトリの `*.toml` を読む。`.toml` 以外のファイルと、`.`
で始まるファイル（エディタのロックファイル `.#<svc>.toml` など）は黙って飛ばす。conf
ディレクトリが無ければ、見出しだけを出す。読めないファイルと、名前から `.toml` を
除いたものがサービス名の規則に合わないファイルは、警告して飛ばし、残りを並べて
から、飛ばした数を告げて終了コード 1 で終わる。

| 列 | 既定で出す | 値 |
| --- | --- | --- |
| `SERVICE` | 出す | ファイル名から `.toml` を除いたもの |
| `PROFILE` | 出す | `AwsProfile` |
| `REGION` | 出す | `AwsRegion` |
| `IMAGE` | 出す | `ImageId` |
| `TYPE` | 出す | `InstanceType` |
| `KEYNAME` | | `KeyName` |
| `IDENTITYFILE` | | `IdentityFile` |
| `SUBNET` | | `SubnetId` |
| `INGRESS` | | `[[security-group.ingress]]` の数 |
| `SSHDPORTS` | | `SshdPorts` を `,` でつないだもの |
| `VOLUMESIZE` | | `VolumeSize` |

値は、設定ファイルを読んだときに効く値である。既定のある項目は、書かれていなければ
既定を出す。値の無い項目（書かれていない `AwsProfile` と `VolumeSize`、`apply` の
前の `ImageId` と `SubnetId`）は `-` と出す。`ImageId` は書かれたままを出し、AMI の
ID に引かない。

### `instance show --svc <svc>`（短縮形 `status`）

サービスのインスタンスの状態を表示する。表示するだけで、設定ファイルにも AWS にも
書き込まない。次を表示する。

- 起動テンプレートの名前。無ければ、`apply` されていないと表示する。止めずに
  続ける。
- インスタンスの ID と状態。無ければ無いと表示する。2 台以上あれば全部を表示する。
  終了の途中のものを除いて 2 台以上あれば、余分なものをインスタンス ID を指して
  `terminate` で終了するよう、標準エラー出力に警告を 1 行出す。
- それぞれのパブリック IPv4 アドレス。付いていなければ無いと表示する。
- それぞれの SSM エージェントの状態（`Online`、`ConnectionLost`、`Inactive`）。
  エージェントが一度も登録していないインスタンスは、未登録と表示する。
- それぞれで、sshd の待ち受けポートを揃える関連付け `<名前>-sshd` が実行し終えたか
  （[design/sshd-ports.md](design/sshd-ports.md#status-の表示)）。
- 焼いていないアプリ。起動テンプレートがあるときだけ、`apps:` の行に出す。
  `deploy` の記録から、`app list` の `STATE` と同じ規則で決め、`unbaked` と
  `lost` のアプリをその順に挙げる（`apps: unbaked timezone-tokyo; lost mise`）。
  どちらも無ければ、`baked` のアプリがあれば `all baked`、無ければ `none` と出す。
  焼いたかどうか分からない記録は数えない。
- アプリの状態。`/<名前>` の下にあるキー `status` のパラメータ
  `/<名前>/<アプリID>/status`（[apps.md](apps.md#アプリの状態)）を、インスタンスの
  表示の後に 1 度、アプリ ID の順に、値と更新からの経過時間とともに表示する。
  インスタンスが無くても表示する。今動いているインスタンスが書いたとみなせない
  値には、経過時間に `stale` を添える。

  ```
  app status:
    idle-shutdown  power off in 42m (at 2026-09-29 06:12:03 UTC; idle 18m since pam, limit 1h)  [3m ago]
    myapp          3 job(s) queued  [12m ago]
  ```

  - 1 つも無ければ `app status: none` と出す。
  - 行は、空白 2 つ、いちばん長いアプリ ID の幅に揃えたアプリ ID、空白 2 つ、値、
    空白 2 つ、`[<経過時間>]` の順である。古い値は `[<経過時間>, stale]` になる。
  - 経過時間は、パラメータの `LastModifiedDate`（UTC）といまの UTC の時刻の差
    である。60 秒未満（時計のずれで負のときを含む）は `just now`、それ以上は
    いちばん大きい単位 1 つで切り捨て、`3m ago`、`2h ago`、`5d ago` のように出す。
    更新時刻が読めなければ `?` と出す。
  - 古い値とは、`pending` か `running` のインスタンスが無いか、そのどれもが値の
    `LastModifiedDate` より後に起動した（`LaunchTime`。停止したものを再開すると
    再開した時刻になる）ものである。アプリは動いているインスタンスからしか書けない
    ので、そのインスタンスが書いた値ではない。インスタンスの中から `shutdown`
    したときや、アプリが書かずに止まったときに、最後の値が今の状態に見えないように
    する。更新時刻か起動した時刻が読めず比べられなければ、古いとはみなさない。
    `reboot` では起動した時刻が変わらないので、再起動の前の値には付かない。
  - 値はアプリがインスタンスから書くので、改行や制御文字など表示できない文字は
    `?` に置き換える。切り詰めない。`SecureString` の値は、復号せずに読むと
    暗号文になるので、値の代わりに `(SecureString)` と出す。
  - `get-parameters-by-path` で `/<名前>` の下を再帰的に読み、名前が
    `/<名前>/<アプリID>/status` の形で、アプリ ID が規則（[`app` の
    コマンド](#app-のコマンド)）に合うものだけを使う。手元の資格情報には
    `ssm:GetParametersByPath` の権限が要る。

### `instance list [--svc <svc>] [--format <列>]`

temt のインスタンスを、1 台 1 行の表で挙げる。temt のインスタンスとは、
`temt:service` タグを持ち、`terminated` でないインスタンスである。`--svc` を
付ければ、そのサービスの設定ファイルで環境が決まり、`temt:service=<svc>` の
ものだけを挙げる。省けば、`--profile` と `--region` で決まる環境の、すべての
サービスのものを挙げる。設定ファイルの無いサービスのインスタンスも出る。
`temt:service` を付ける前に起動したインスタンスは出ない。`status` は `Name` で
探すので、そちらには出る。並べる順は、
`temt:service` の値、起動時刻、ID の順である。SSM エージェントは見ない。それは
`status` が出す。

| 列 | 既定で出す | 値 |
| --- | --- | --- |
| `ID` | 出す | インスタンスの ID |
| `SERVICE` | 出す | `temt:service` の値 |
| `STATE` | 出す | 状態 |
| `TYPE` | 出す | インスタンスタイプ |
| `LAUNCHED` | 出す | 起動時刻。止めたものを再開すると、再開した時刻になる |
| `IMAGE` | | 起動に使った AMI の ID |
| `IP` | | パブリック IPv4 アドレス |

### `template show --svc <svc>`

起動テンプレート（[design/launch-template.md](design/launch-template.md)）の詳細を
表示する。表示するだけで、設定ファイルにも AWS にも書き込まない。次を表示する。

- 既定バージョンの内容。バージョン番号と作成時刻、temt が管理する項目。`SubnetId`
  には、そのサブネットが属する VPC を添える。`VolumeSize` は、入っていなければ
  `(not set)` と出す。AWS が補った項目は出さない。
- テンプレートの `ImageId` が指す AMI の名前、作成日、状態、ルートボリュームの
  大きさ。EBS のルートボリュームが無ければ、大きさは `(no EBS root volume)` と
  出す。AMI が見つからなければその旨。
  加えて `temt:service=<svc>` の最新の AMI の名前と ID を示し、テンプレートの
  ものより新しければ、それと分かるようにする。
- バージョンの一覧。1 行に 1 バージョンで、番号、既定の印、作成時刻、`ImageId`、
  `InstanceType`、`SubnetId`。

設定ファイルとは比べない。次の `apply` が起動テンプレートの何を変えるかは、`diff` が
出す。

### `sg` のコマンド

セキュリティグループの受信規則
（[design/security-group.md](design/security-group.md)）を扱う。`sg list`、
`sg add`、`sg remove` は設定ファイルの `[[security-group.ingress]]` だけを
読み書きし、AWS は呼ばない。AWS 側を変えるのは `apply` だけで、`sg add` と
`sg remove` の後に `apply` を実行して反映する。`sg diff` と `sg show` は AWS を
読むが、書かない。どれもロックは取らない。

規則は `<ポート>` と `<CIDR>` で指す。引数の誤りは、設定ファイルを読む前に知らせる。

- `<ポート>`: `22` のようなポート 1 つか、`8000-8010` のような範囲（0 から 65535 で、
  下限が上限以下）に、`/tcp` か `/udp` を付けたもの。付けなければ `tcp` とする。
  `icmp` と書けば ICMP で、ポートは取らない。
- `<CIDR>`: IPv4 か IPv6 の CIDR。`/` が無ければアドレス 1 つ（`/32` か
  `/128`）とする。設定ファイルの `Cidr` と同じく、ホスト部にビットが立っていれば
  引数の誤りとする。省くと、手元のグローバル IP アドレスを調べて、IPv4 は `/32`、
  IPv6 は `/64` にし、使った CIDR を知らせる
  （[design/security-group.md](design/security-group.md#グローバル-ip-アドレス)）。

設定ファイルを書き換えるときは、`apply` の手順 2 と同じく、既に書かれている
項目の順序とコメントを変えない。規則は最後の規則の後ろに足す。規則が無ければ
`[security-group]` の末尾に、それも無ければファイルの末尾に足す。`Protocol` は、
既定の `tcp` なら書かない。規則を消すときは、その規則の前後にあったコメントを
残し、空行は重ねない。最後の規則を消したとき、`[security-group]` の見出しを
書いてあれば、見出しとその下のコメントを残す。見出しが無ければ書き足さず、残す
コメントは前のテーブルの後ろに置く。前にテーブルが無ければ、コメントを残すために見出しを
書く。設定ファイルが無ければ、`apply` を実行するよう促して終了する。

書き換える前に設定ファイルを読み直し、規則が最初に読んだときと違えば（グローバル
IP アドレスを調べている間に直されたなど）、書かずに終了する。書き換えた結果も読み直し、
期待した規則と違うか、規則のほかの項目が変わっていれば、書かずに終了して手で直す
よう告げる。規則を他のテーブルを挟んで分けて書いたファイル、`[security-group]` の
見出しと規則を離して書いたファイル、中身の無いインラインテーブル
（`security-group = {}`）で書いたファイルで起きることがある。

- `sg list --svc <svc> [--format <列>]`: 設定ファイルの受信規則を、書かれた順に
  1 つ 1 行の表で挙げる。

  | 列 | 既定で出す | 値 |
  | --- | --- | --- |
  | `PORT` | 出す | `22/tcp`、`8000-8010/udp`、`icmp` の形。`sg remove` の `<ポート>` にそのまま渡せる |
  | `CIDR` | 出す | `Cidr` |
  | `DESCRIPTION` | 出す | `Description` |

- `sg add --svc <svc> <ポート> [<CIDR>] [--description <説明>]`: 設定ファイルに
  規則を足す。`<CIDR>` を省いて IPv4 と IPv6 の両方が取れれば、2 つ足す。
  プロトコル、ポート、CIDR が同じ規則が既にあれば足さず、
  `--description` があれば説明だけを書き換える。説明は設定ファイルの
  `Description` と同じ制約に従い、外れれば引数の誤りとする。空の説明は、説明を
  消す。足した規則と説明を書き換えた規則を知らせ、`apply` で反映するよう添える。
  何も変えなければ、その旨を知らせる。
- `sg remove --svc <svc> <ポート> [<CIDR>]`: 設定ファイルから規則を消す。
  `<CIDR>` を省けば、グローバル IP アドレスから作った CIDR の規則を消す。無い規則は
  無いと知らせる。消した規則を知らせ、`apply` で反映するよう添える。1 つも
  消せなければ、終了コード 1 で終わる。
- `sg diff --svc <svc>`: 次の `apply` が受信規則をどう変えるかを、1 つ 1 行で
  標準出力に書く。比べる相手は、`SubnetId` が属する VPC にある `<名前>` の
  セキュリティグループである。行の頭は `+`（足す）、`~`（説明を直す）、`-`
  （消す）のどれかで、続けて `PORT`、送信元、説明を、空白で揃えて並べる。`~` の
  行の説明は `<今の説明> -> <新しい説明>` と書く。説明が無ければ `-` と書く。
  temt が表せない規則は、`PORT` を
  `<プロトコル>:<ポートの下限か ICMP の種類>:<上限かコード>` の形で書く。
  ポートを持たないプロトコルは AWS が返したまま（番号）にする。すべての
  プロトコルは `all`、IPv6 の送信元を持つ IPv4 の ICMP は `icmpv4` と書く。
  送信元は他のセキュリティグループの ID かプレフィックスリストの ID で書く。並べる
  順は `+`、`~`、`-` の順で、`+` と `~` は設定ファイルの順、`-` は AWS から読んだ
  順である。違いが無ければ、標準出力には何も書かず、その旨を標準エラー出力に
  知らせる。終了コードは、違いの有無によらず 0 とする。セキュリティグループが
  無ければ（`apply` の前か、`SubnetId` を別の VPC のものに変えたあと）、すべての
  規則を `+` で出す。`SubnetId` が書かれていないときも、次の `apply` が選ぶことを
  知らせて、すべての規則を `+` で出す。
- `sg show --svc <svc>`: セキュリティグループを標準エラー出力に表示する。項目は、
  名前、ID、VPC、説明、タグ、AWS 側の受信規則の数である。`SubnetId` の VPC に
  無ければ、次の `apply` が作ることを表示する。ほかの VPC に同じ名前の
  セキュリティグループがあれば、ID と VPC を挙げ、`destroy` が消すことを添える。
  `SubnetId` が書かれていなければ、VPC が決まらないので、そのことを表示し、同じ
  名前のセキュリティグループを ID と VPC で挙げるだけにする。受信規則の中身は
  出さない。定義は `sg list` で、AWS との違いは `sg diff` で見る。

### `app` のコマンド

サービスのインスタンスの中で動くアプリの値と記録を、手元から扱う。`--svc` を
省いた `app list` だけは、手元のアプリを見る。値は SSM パラメータ
`/<名前>/<アプリID>/<キー>` に置く。キー `deploy` は、アプリを入れた
ときの記録で、temt が書く。次の項目を持つ JSON である。

| 項目 | 書くもの | 値 |
| --- | --- | --- |
| `name` | `deploy` | アプリ名 |
| `version` | `deploy` | 最後に入れた版 |
| `user` | `deploy` | `install` を実行したユーザー |
| `deployed` | `deploy` | 入れ終えた時刻（UTC の `2026-09-20T03:00:00Z` の形） |
| `instance` | `deploy` | 入れたインスタンスの ID。焼くと `bake` が消すので、最後に入れた版をまだ焼いていないときだけある |
| `options` | `deploy` | 最後に入れたときに使ったオプションのうち、コマンドラインか前の記録から来たもの。オプションの名前から値への JSON のオブジェクト。既定で埋めたものは書かず、1 つも無ければ項目ごと書かない |
| `baked_version` | `bake` | AMI に焼いた版 |
| `baked_image` | `bake` | その版が入っている、いちばん新しい AMI の ID。焼き直すたびに付け替える |
| `baked_options` | `bake` | AMI に焼いた版の `options`。1 つも無ければ項目ごと書かない |

`options` と `baked_options` を除く項目の値は文字列である。記録は、日本語などの値も
`\u` の形にせず、UTF-8 のまま書く。ただし SSM は `{{` を含む値をほかのパラメータの
参照として断るので、文字列の中で `{` が続くところは、前の `{` を `\u007b` と書く。

記録は SSM パラメータなので、誰でも書き換えられる。JSON のオブジェクトでない記録と、
UTF-8 で書けない値（対にならないサロゲートを表す `\u` の形）を含む記録は、読めない
記録とする。`options` か `baked_options` の形が違えば（名前から値への対応でない、
名前がオプションの名前の規則に外れる、値が制御文字を含む）、その項目だけを読めない
ものとし、記録を書き直すときは、JSON として読んだ値をそのまま書き戻す。

`deploy` は、前の記録の `baked_version`、`baked_image`、`baked_options` を引き継ぐ。
新しい版を入れても、焼くまでは AMI に前の版が残っているからである。同じ版を入れ直しても
`instance` を書く。`install` やアプリのファイルが変わっていることがあるからである。
`app remove` は記録を消すので、焼く前のアプリが AMI に残っていても、記録からは
分からない。キー `status` は、アプリが
インスタンスから書くいまの状態で、`status` が表示する
（[apps.md](apps.md#アプリの状態)）。`app list`、`app show`、`app get`、`app set`、
`app unset` は、表示するか値 1 つを書き換えるだけなので、ロックは取らない。

アプリ ID とキーは、英小文字で始まり、英小文字・数字・ハイフンが続き、英小文字か
数字で終わる 64 文字以内の名前とする。`/` を含む階層は許さない。外れた名前は、AWS を
呼ぶ前に引数の誤りとする。`app set` と `app unset` は、キー `deploy` を引数の誤りと
する。

- `app list [--svc <svc>] [--format <列>]`: `--svc` を付ければ、`/<名前>` の下に
  `deploy` の記録があるアプリと、アプリ ID で `deploy` できるアプリ（conf
  ディレクトリの `apps/` にあるものと、temt と一緒に配るもの）を合わせて、アプリ
  1 つ 1 行の表で挙げる。
  並べる順はアプリ ID の順である。
  記録が読めない（[`app` のコマンド](#app-のコマンド)）ときや、`manifest.toml` が
  読めないときは、警告してその分の値を空にする。conf ディレクトリの `apps/` と
  temt と一緒に配るアプリの場所のどちらでも、ディレクトリでないもの（壊れたリンクを
  含む）とアプリ ID の規則に外れた名前は挙げない。手元のアプリの値は、`deploy` がアプリ ID で使うもの（conf ディレクトリの
  `apps/` にあればそれ、無ければ temt と一緒に配るもの）から取る。

  | 列 | 既定で出す | 値 |
  | --- | --- | --- |
  | `ID` | 出す | アプリ ID |
  | `NAME` | 出す | アプリ名。記録のものを、記録に無いか読めなければ `manifest.toml` のものを出す |
  | `VERSION` | 出す | 最後に入れた版（記録の `version`） |
  | `DEPLOYED` | 出す | 入れ終えた時刻 |
  | `STATE` | 出す | 最後に入れた版を焼いたかどうか（下の表） |
  | `BAKED` | 出す | 起動テンプレートが指す AMI に入っている版。`baked_image` がその AMI のときの `baked_version` |
  | `LOCAL` | 出す | 手元のアプリの `manifest.toml` の版 |
  | `PATH` | | 手元のアプリのディレクトリ |

  `STATE` は、記録と、起動テンプレートの既定バージョンの `ImageId`、`start` と同じ
  条件で探したインスタンスから決める。`shutting-down` のインスタンスは、無いものと
  みなす。

  | `STATE` | 条件 | 意味 |
  | --- | --- | --- |
  | `unbaked` | `instance` があり、そのインスタンスがある | 最後に入れた版は、そのインスタンスにだけある |
  | `lost` | `instance` があり、そのインスタンスが無い | 焼く前にインスタンスが終了し、最後に入れた版は無くなった |
  | `baked` | `instance` が無く、`baked_image` がテンプレートの AMI | 最後に入れた版が AMI に入っている |
  | `lost` | `instance` が無く、`baked_image` がテンプレートの AMI でない | `apply` で別の AMI に替えたなどで、AMI に入っていない |
  | `-` | どちらも無い | 焼いたかどうかを記録する前の `deploy` が書いた記録 |

  `--svc` を省けば、アプリ ID で `deploy` できるアプリだけを、同じ規則で挙げる。
  AWS は呼ばない。`VERSION`、`DEPLOYED`、`STATE`、`BAKED` はサービスごとの値なので、
  列に持たない。

  | 列 | 既定で出す | 値 |
  | --- | --- | --- |
  | `ID` | 出す | アプリ ID |
  | `NAME` | 出す | `manifest.toml` のアプリ名 |
  | `LOCAL` | 出す | `manifest.toml` の版。`--svc` を付けたときの `LOCAL` と同じ |
  | `PATH` | 出す | アプリのディレクトリ。`--svc` を付けたときの `PATH` と同じ |
  | `DESCRIPTION` | | `manifest.toml` の説明 |

- `app show --svc <svc> <アプリID>`: `deploy` の記録と、アプリの階層のすぐ下の
  キーの一覧（キー、更新時刻）を、標準エラー出力に表示する。値は出さない。記録が
  無ければ、入っていないと表示する。規則に外れたキーも挙げる。記録の `options` と
  `baked_options` は、`<名前>=<値>` を空白で区切って並べ、値はそのままコマンドラインに
  打てるよう、要ればシェルの引用符で囲む。形が違って読めなければ `(unreadable)` と
  出す。アプリ ID で `deploy` できるアプリがあれば、続けてその `manifest.toml` が
  宣言するオプション（名前、既定、説明）を挙げる。既定は値と同じく引用符で囲み、既定の
  無いものは `(required)` と出す。`manifest.toml` が読めなければ警告する。記録と
  キーはインスタンスからも書けるので、改行や ESC など表示できない文字は `?` に
  置き換える。ただしオプションの値と、宣言の見出しの `manifest.toml` の版、既定、
  説明で置き換えるのは、端末を乱す文字だけである
  （[アプリのオプション](#アプリのオプション)）。記録も値も無く、アプリ ID で
  `deploy` できるアプリも無ければ、アプリ ID の打ち間違いとみなして終了する。
- `app get --svc <svc> <アプリID> <キー>`: 値を 1 つ、そのまま UTF-8 で
  標準出力に書く。改行を足さず、改行や ASCII 以外の文字もそのまま出す。値が
  無ければ終了する。`SecureString` の値は、復号せずに読むと暗号文になるので、
  出さずに終了する。`deploy` の記録も読める。
- `app set --svc <svc> <アプリID> <キー>=<値>`: 値を 1 つ `String` で書く。
  無ければ作り、あれば上書きする。キーと値は 1 語で取り、最初の `=` で分ける。
  値は `=` を含んでもよい。値は加工せず、`-` で始まる値もそのまま受け取る。
  `=` の無い語は引数の誤りとする。空の値は SSM が受け付けないので、引数の
  誤りとする。UTF-8 として読めない値も、`app get` で出せなくなるので引数の
  誤りとする。既にある値が `String` でなければ、上書きで型を変えられないので、
  先に `app unset` するよう告げて終了する。`deploy` の記録が無いアプリには
  書かずに終了する。作ったか上書きしたかを知らせる。
- `app unset --svc <svc> <アプリID> <キー>`: 値を 1 つ消す。確認は取らない。
  `deploy` の記録が無くても消せる。無ければ無いと知らせ、誤りにしない。

### `app deploy --svc <svc> <アプリIDまたはパス> [<名前>=<値>...] [--reset] [--user <ユーザー>] [--bake] [--yes]`（短縮形 `deploy`）

アプリを、動いているインスタンスに入れる。ロールのポリシーには触らない。アプリが
使う権限は、設定ファイルの `[[role.policy.<ポリシー名>]]` に書いて `apply` で付ける
（[conf.md](conf.md#role)）。S3 のバケットなど、アプリが使う AWS のリソースも temt は
作らない。アプリは 1 つのディレクトリである。

```
<アプリID>/
    manifest.toml  アプリ名 name と版 version（必須）、説明 description と
                   install を実行するユーザー user、オプションの宣言
                   [options.<名前>]（任意）
    install        導入の bash スクリプト。必須
    uninstall      外す bash スクリプト。任意。無ければ app remove で外せない
    ...            install が使うファイル。temt-options.env は temt が足すので置けない
```

`install` を実行するインスタンスのユーザーは、`--user` の値、無ければ
`manifest.toml` の `user`、それも無ければ root とする。`uninstall` は、`app remove` の
1 のとおり、記録した `user` で実行する。ユーザー名は、英小文字か `_` で
始まり、英小文字・数字・`_`・`-` が続く 32 文字以内とし、外れた名前は引数か
`manifest.toml` の誤りとする。root 以外のユーザーなら `sudo -n -H -u <ユーザー>` を
通して実行するので、`HOME` はそのユーザーのホームになり、`PATH` は sudo の
`secure_path` になる。そのユーザーの `install` は、root が要る操作を自分で `sudo`
する。root なら、ssh の `sudo -n` の中でそのまま実行する。

`install` と `uninstall` は、自分のファイルをスクリプトのあるディレクトリから探し、カレント
ディレクトリに依存しないように書く。temt はカレントディレクトリを `/` にして
実行する。実行するユーザーが入れるとは限らないからである。`install` は何度実行
してもよいものにする。常駐するものは systemd などで起動し、`install` から
バックグラウンドに回すなら出力を `/dev/null` へ向ける。
`install` の出力を引き継いだプロセスが残ると、ssh が終わらず、`deploy` がロックを
持ったまま止まる。ファイルのモードは、グループと他人の書き込み、setuid、setgid、
sticky を落として送る。

引数が `/` を含めばパス、含まなければアプリ ID とする。パスなら、その
ディレクトリを使い、最後の要素をアプリ ID とする。シンボリックリンクは解かずに
名前を取る。アプリ ID なら、conf ディレクトリの `apps/<アプリID>/` を探し、
無ければ temt と一緒に配るアプリを使う。利用者は同じアプリ ID で置けば、temt と
一緒に配るアプリの代わりに自分のものを使える。`apps/<アプリID>` がディレクトリで
ない（ファイルや壊れたリンク）ときは、temt と一緒に配るアプリがあれば、警告して
それを使う。どちらにも無ければ、使えるアプリ ID を挙げ、近い名前があれば
`did you mean` で添えて終了する。アプリ ID の規則は `app` のコマンドと同じである。

1. アプリのディレクトリを探し、どこから取ったかを知らせる。リンクなら、その先も
   添える。`manifest.toml` を読み、`install` があり、`temt-options.env` が無いことを
   確かめる。コマンドラインで与えたアプリのオプションを宣言と照らす（[アプリのオプション](#アプリのオプション)）。
   ここまでは AWS にもインスタンスにも触れない。
2. ロックを取り、起動テンプレートがあることを確かめ、`start` と同じ条件で
   インスタンスを探す。`running` のものが 1 台でなければ終了する。無ければ
   `start` を促し、`pending` なら `start` が終わるのを待つよう促し、停止したもの
   か停止の途中なら `start` で再開するよう促す。2 台以上なら `start` と同じく
   列挙して止める。自分では起動も再開もしない。
   `ssh -T <名前>` でつなぎ、`sudo -n` で `/var/lib/cloud/data/instance-id` を読んで、
   探したインスタンスにつながったことを確かめる。つながらないか、`sudo` が使えないか、
   別のインスタンスにつながれば、何も変えずに終了する。ssh の `ProxyCommand` の
   `proxy` には `--profile` が届かず、設定ファイルの `AwsProfile` か、無ければ AWS の
   既定の規則で決まるプロファイルで探すからである。`--profile` を付けていて、それが
   `AwsProfile` と違うときだけ、そのことを添える。`ProxyCommand` の待ちの知らせと ssh
   の誤りは、そのまま標準エラー出力に出す。
   `install` を実行するユーザーが root でなければ、`id -u` でインスタンスにいることを
   確かめ、いなければ何も変えずに終了する。
   前の記録を読み、使うオプションの値を決めて、1 つ 1 行で出どころとともに知らせる。
   記録が SSM パラメータに収まることを確かめ、ディレクトリを tar.gz にする。記録を
   SSM から読めなければ（権限が無いなど）、`--reset` を付けていても、何も変えずに
   終了する。
   `--bake` なら、`bake` の 3 と同じく、テンプレートが設定ファイルと揃っていることと、
   インスタンスのルートボリュームが `VolumeSize` より大きくないことを確かめ、入れる
   ことと `bake` がすることを挙げて確認する。
3. `ssh -T <名前>` でつなぎ、tar.gz を標準入力に流す。インスタンスの上では `sudo` で、
   `/opt/temt/apps/` の下の一時ディレクトリに展開し、`/opt/temt/apps/<アプリID>/` と
   入れ替える。途中で失敗すれば一時ディレクトリを消し、古いものが残る。前に止まって
   残った一時ディレクトリは、はじめに消す。続けて、
   もう一度つないで、カレントディレクトリを `/` にし、そのユーザーで
   `bash /opt/temt/apps/<アプリID>/install` を実行する。
   ssh の出力は標準エラー出力に流す。
4. 記録 `/<名前>/<アプリID>/deploy` を書く。`user` は `install` を実行したユーザー、
   `deployed` は `install` を終えたときの手元の時刻を UTC で、`instance` は入れた
   インスタンスの ID を、`options` は 2 で決めた値のうち出どころが `given` か `kept` の
   ものを書く。前の記録の `baked_version`、`baked_image`、`baked_options` は引き継ぐ。
5. `--bake` なら、`bake` の 5〜9 を、同じロックを持ったまま行う。付けなければ、焼く
   まで次のインスタンスに入らないことを知らせる。

ディレクトリは、隠しファイルも含めてまるごと送る。アプリのディレクトリが
シンボリックリンクなら辿るが、中のリンクはリンクのまま送るので、アプリの外を
指すものはインスタンスで切れる。Ctrl-C で ssh を止めても、インスタンスの上の
`install` は走り続けることがある。

途中で失敗しても巻き戻さない。2 までに失敗すれば何も変わらない。3 で送れなければ、
古いディレクトリが残る。`install` が失敗すれば、新しいディレクトリが残る。どちらも、
もう一度 `deploy` すれば揃う。記録は `install` が成功したときだけ書く。失敗したら
`--bake` を付けていても焼かない。記録の `options` も前のままなので、やり直すときは
同じオプションを付け直す。

### アプリのオプション

アプリは、`deploy` で値を変えられるオプションを `manifest.toml` の
`[options.<名前>]` で宣言する。名前の規則はアプリ ID と同じである。項目は次の
とおりで、ほかの項目があれば `manifest.toml` の誤りとする。

| 項目 | 必須 | 中身 |
| --- | --- | --- |
| `description` | 必須 | 説明。空でない文字列で、制御文字を含まない。`app show` と、値の誤りに出す |
| `default` | 任意 | 既定の値。文字列で、空でもよい。省けば既定の無いオプションになり、`deploy` のたびにコマンドラインか前の記録から値が要る |
| `pattern` | 任意 | Python の正規表現。値の全体が `pattern` に一致することを求める。`default` も一致しなければ `manifest.toml` の誤りとする |

値は文字列で、制御文字（Unicode の Cc。改行、タブ、ESC など）を除けば何でも使える。
長さの上限は設けず、代わりに記録の大きさを確かめる。コマンドラインの `<名前>=` は既定に
戻す指定なので、コマンドラインから空の値は与えられない。

コマンドラインでは、アプリの後ろに `<名前>=<値>` の 1 語を並べる。最初の `=` で分け、
値は加工しない。`=` の無い語、名前の規則に外れた名前、同じ名前の繰り返し、制御
文字を含む値、UTF-8 として読めない値は、引数の誤りとする。アプリより先に置いた
`<名前>=<値>`（`/` を含まず `=` を含む 1 語め）も、そのことを告げて引数の誤りとする。
宣言していない名前と、`pattern` に一致しない値は、手順 1 で、近い名前や説明を添えて
終了する。

使う値は、宣言したオプションごとに次の順で決める。

1. コマンドラインに `<名前>=<値>` があれば、その値（出どころ `given`）。
2. 前の記録の `options` にあれば、その値（`kept`）。`--reset` を付ければ、前の記録
   から何も引き継がない。`<名前>=`（空の値）は、その名前を引き継がない。
3. 宣言の `default`（`default`）。既定の無いオプションは、ここで値が無ければ
   終了する。既定の無いオプションに `<名前>=` を付けたときは、手順 1 で終了する。

記録に書く `options` は、1 と 2 で決まった値だけである。知らせの行は
`option <名前>=<値> (<出どころ>)` の形で、値は要ればシェルの引用符で囲む。前の記録に
よっては、次のようにする。前の記録の `baked_options` だけが読めないときは止めず、
書かれていたままの値で引き継ぐ。

| 前の記録 | 振る舞い |
| --- | --- |
| 無い（初めての `deploy`、`app remove` や `destroy` の後） | 引き継ぐものは無い |
| SSM から読めるが、記録が読めないか、`options` の形が違う | 何も変えずに終了し、`--reset` を付けて指定し直すよう告げる。アプリがオプションを宣言していなければ、引き継ぐものが無いので止めず、形の違う `options` は警告して捨てる |
| アプリが宣言していない名前がある | 警告して外し、続ける。記録からも消える |
| 引き継ぐ値が `pattern` に一致しない | 何も変えずに終了し、`<名前>=<値>` か、既定があれば `<名前>=` を付けるよう告げる |

記録は SSM パラメータ（標準）に収まる大きさでなければならない。手順 2 で、この
`deploy` が書く記録と、続けて焼いたときの記録（`options` が `baked_options` にも
写ったもの）の大きさを、UTF-8 のバイト数で見積もり、どちらかが 4096 バイトを超えれば、
何も変えずに終了する。

使う値は、宣言したすべてのオプションについて、アプリのディレクトリのすぐ下に足す
ファイル `temt-options.env` で `install` に渡す。tar.gz に root の持ち物のモード 644 で
入れて送るので、値はコマンドラインを通らない。1 行に 1 つ、宣言の順に、
`TEMT_OPTION_<名前>=<値>` の形で書く。変数の名前は、オプションの名前を大文字にし、`-` を
`_` にしたものである。値は Python の `shlex.quote` でシェルの引用符で囲むので、bash の
`.` で読み込んでも展開されない。1 行めは、アプリ ID と版を書いたコメントである。
オプションを宣言していないアプリには置かない。ディレクトリとともに入れ替わり、焼けば
AMI に残るので、`uninstall` も同じ値を読める。

オプションの値と、`manifest.toml` から来る版、説明、既定をメッセージや `app show` に
出すときは、端末を乱す文字だけを `?` に置き換える（`list` の表では、ほかの値と同じく
表示できない文字をすべて置き換える）。制御文字（Unicode の Cc）、対にならないサロゲート
（Cs）、行と段落の区切り（Zl、Zp）、文字の向きに関わる制御文字（U+061C、U+200E、
U+200F、U+202A〜202E、U+2066〜2069）である。全角空白や、ゼロ幅接合子でつないだ
絵文字などは、そのまま出す。値は制御文字を含まないので、値の表示がそのまま打てない
のは、行と段落の区切りか、文字の向きに関わる制御文字を含む値だけである。

記録の値は暗号化されず、`temt-options.env` は AMI に残ってインスタンスの誰からも
読めるので、オプションには秘密の値を渡さない。

### `app remove --svc <svc> <アプリID> [--user <ユーザー>] [--bake] [--yes]`

アプリを、動いているインスタンスから外す。インスタンスの条件は `deploy` の 2 と
同じである。アプリのために書いた `[[role.policy.<ポリシー名>]]` は、外したあとで
設定ファイルから消して `apply` する。

1. `deploy` の 2 と同じく、探したインスタンスにつながることを確かめる。
   インスタンスの上に `/opt/temt/apps/<アプリID>/` と、その中の
   `uninstall` があることを確かめる。`uninstall` が無ければ、何も変えずに
   終了する。ディレクトリも記録も無ければ、アプリ ID の打ち間違いとみなして
   終了する。ディレクトリがあれば、`uninstall` を実行するユーザーを、`--user` の
   値、無ければ記録の `user` とする。記録が無いか、読めないか、`user` が無ければ、
   root で実行することを警告して root とする。
   記録の `user` がユーザー名の規則に外れていれば、値は出さずに、`--user` で
   指すよう告げて終了する。ユーザーが root でなければ、`deploy` の 2 と同じく
   インスタンスにいることを確かめる。`--bake` なら、ここまで確かめてから
   `deploy` の 2 と同じく、ユーザーも挙げて確認する。ディレクトリが無ければ、
   警告して 3 へ進む。
2. カレントディレクトリを `/` にし、そのユーザーで
   `bash /opt/temt/apps/<アプリID>/uninstall` を実行し、成功したら root で
   ディレクトリを消す。失敗したら、記録を残して終了する。
   Ctrl-C で止めても、インスタンスの上の `uninstall` は走り続けることがある。
3. 状態 `/<名前>/<アプリID>/status` を消してから、記録 `/<名前>/<アプリID>/deploy`
   を消す。状態は、残すと `status` が外したアプリの古い状態を出し続けるからである。
   記録を最後に消すのは、途中で失敗しても、記録が残っていればやり直しで続きから
   進めるためである。ほかのアプリの値と、ロールのポリシーは消さない。
4. `--bake` なら、`bake` の 5〜9 を、同じロックを持ったまま行う。付けなければ、焼く
   まで AMI には残ることを知らせる。

### temt と一緒に配るアプリ

`src/temt/apps/<アプリID>/` に置き、パッケージに入れて配る。`deploy` はアプリ ID で
指されたものが conf ディレクトリの `apps/` に無ければ、これを使う。

| アプリ ID | 中身 |
| --- | --- |
| `idle-shutdown` | 誰も使っていなければ電源を切る（[apps/idle-shutdown.md](apps/idle-shutdown.md)） |
| `swapfile` | `/swapfile` を swap に使う（[apps/swapfile.md](apps/swapfile.md)） |
| `timezone-tokyo` | タイムゾーンを Asia/Tokyo にする（[apps/timezone-tokyo.md](apps/timezone-tokyo.md)） |

### `keypair` のコマンド

EC2 のキーペアと、手元の鍵 `~/.ssh/temt/keys/<キーペア名>` を扱う。どれも
`--svc` を取らず、環境は `--profile` と `--region` で決まる。ロックは取らない。

フィンガープリントは、[design/keypair.md](design/keypair.md) と同じく、公開鍵から
`ssh-keygen -l` と同じ `SHA256:` の形で計算する。EC2 のキーペアは
`describe-key-pairs --include-public-key` で取った公開鍵を使う。EC2 の
`KeyFingerprint` は、RSA では登録のしかたで計算が変わり（EC2 が作れば秘密鍵の
SHA-1、取り込めば公開鍵の MD5）、ED25519 でも `SHA256:` が付かず末尾に `=` が付く
ことがあるので、比べない。キーペアを使っているかは、そのアカウントとリージョンに
あるすべての起動テンプレートの、すべてのバージョンの `KeyName` で決める。

**`keypair list [--format <列>]`。** `temt:keypair` タグの付いたキーペアを、名前の
順に 1 つ 1 行の表で挙げる。

| 列 | 既定で出す | 値 |
| --- | --- | --- |
| `NAME` | 出す | キーペア名 |
| `FINGERPRINT` | 出す | フィンガープリント |
| `CREATED` | 出す | 作成日時 |
| `LOCAL` | 出す | 手元の `~/.ssh/temt/keys/<キーペア名>` との照合 |
| `USED` | 出す | そのキーペアを使っている起動テンプレートのバージョン |
| `ID` | | キーペアの ID |
| `TYPE` | | 鍵の種類 |

`LOCAL` は、一致すれば `matches`、違えば `differs`、読めなければ `unreadable`、
手元に無ければ `-` である。読めない鍵は、`ssh-keygen` が言う理由を添えて警告する。
EC2 が公開鍵を返さなければ、`FINGERPRINT` を `-` とし、手元に鍵があれば `LOCAL` を
`unknown` とする。手でタグを付けたキーペアの名前がキーペア名の規則に合わなければ、
`keys/` の外を指さないよう、手元の鍵は探さず `-` とする。

**`keypair show <キーペア名またはファイル>`。** 引数に `/` があれば手元の鍵の
ファイル、無ければキーペア名とする。キーペア名には `/` を使えないからである。
今のディレクトリの鍵は `./` を付けて指す。`-` で始まる引数は
コマンドラインオプションとみなすので、`-` で始まる名前のキーペアは表示できない。
ファイルは、AWS に問い合わせる前に、あってファイルであることを確かめる。

- キーペア名なら、管理下かどうかを問わず、そのキーペアの ID、種類、作成日時、
  タグ、フィンガープリント、`KeyFingerprint`、公開鍵、使っている起動テンプレートの
  バージョンと、一致する手元の鍵を表示する。手元の鍵は、`apply` が鍵の不一致の
  ときに手がかりを探すのと同じ場所（`~/.ssh/temt/keys/` と `~/.ssh/id_*`）から探す
  （[design/keypair.md](design/keypair.md#鍵の不一致)）。無ければエラーにする。
- ファイルなら、秘密鍵か公開鍵か、種類とビット数、コメント、フィンガープリント、
  公開鍵と、その環境のすべてのキーペアのうちフィンガープリントが一致するものを
  表示する。空でない最初の行が `-----BEGIN ` で始まり `PRIVATE KEY-----` で
  終われば秘密鍵とし、`ssh-keygen -y` で公開鍵を取り出して、隣の
  `<ファイル>.pub` と一致するかも示す。パスフレーズ付きなどで
  取り出せなければ、隣の `.pub` があればそれを使い、無ければ取り出せない理由だけを
  表示する。

**`keypair create <キーペア名>`。** 手元に新しい鍵を作り、キーペアとして登録する。
既にある鍵を取り込む手段は設けない。

1. 手元に `~/.ssh/temt/keys/<キーペア名>` か `<キーペア名>.pub` があれば、
   エラーにして終了する。秘密鍵があれば、その鍵を登録するには `KeyName` にその
   名前を書いて `apply` するよう添える。
2. EC2 に同じ名前のキーペアがあれば、エラーにして終了する。
3. `apply` と同じく `ssh-keygen -t ed25519` でパスフレーズ無しの鍵を作り、公開鍵を
   `import-key-pair` で登録して `temt:keypair=<キーペア名>` を付ける。AWS が登録を
   断れば、作った鍵を消してエラーにする。もう一度 `create` できるようにするため
   である。接続の失敗などで答えが得られなければ、登録されたか分からないので、
   作った鍵は残す。
4. キーペアの ID とフィンガープリントを知らせる。

**`keypair delete <キーペア名> [--yes]`。** EC2 のキーペアと手元の鍵を消す。鍵を
作り直しやすくするためのコマンドである。

1. キーペアが無ければ、エラーにして終了する。`temt:keypair` タグが無ければ、
   temt が作ったものではないと告げて終了する。管理下に入れたければ、利用者が手で
   タグを付ける。
2. そのキーペアを使っている起動テンプレートのバージョンと、そのキーペアで起動して
   まだ終了していないインスタンス（`pending`、`running`、`stopping`、`stopped`）を
   警告として挙げる。使われていても止めない。サービスの `KeyName` がそのキーペアを
   指していて `IdentityFile` が既定のままなら、次の `apply` が新しい鍵を作って同じ
   名前で登録し直す。挙げたインスタンスには前の鍵しか入っていないので、ログイン
   できなくなる。手元の鍵を消すときは、それが環境をまたいで 1 つであることも警告
   し、同じ鍵を登録した他のリージョンやアカウントでも `keypair delete` するよう
   促す。手元の鍵が消えるので、そこのインスタンスにもログインできなくなる。
   そこでも `keypair delete` しなければ、そこの `apply` は鍵の不一致で止まる。他の
   環境は調べない。
3. キーペアと、消す手元の鍵を挙げて確認する。手元で消すのは
   `~/.ssh/temt/keys/<キーペア名>` と `<キーペア名>.pub` のうちあるものだけで、設定
   ファイルの `IdentityFile` や ssh の設定が指していても消す。他の場所の鍵には
   触れない。
4. `delete-key-pair` でキーペアを消し、手元の鍵を消す。キーペアを消せなければ、
   手元の鍵は残す。

### `ssh proxy --svc <svc> [ポート]`（短縮形 `proxy`）

ssh の ProxyCommand として動く。ポートの既定は 22 で、1 から 65535 の整数だけを
受け付ける。ロックは取らない。

インスタンスへの経路は 2 つあり、環境変数 `TEMT_LOGIN` の値がそれぞれに対応する。

- **`ssm`: Session Manager 経由。** `aws ssm start-session --target <instance-id>
  --document-name AWS-StartSSHSession --parameters portNumber=<ポート>` で接続する。
  通信は https で AWS の API へ向かうので、セキュリティグループの受信許可も、
  sshd のポート（`SshdPorts`）で外へ出られるネットワークも要らない。クライアントに
  `session-manager-plugin` が要る。
- **`direct`: 直接接続。** インスタンスのパブリック IPv4 アドレスへ TCP で接続する。
  セキュリティグループの受信許可と、クライアントから sshd のポートへ出られる
  ネットワークが要る。

`proxy` は、接続のたびに環境変数 `TEMT_LOGIN` を読んで経路を選ぶ。無いか空なら
`ssm`、`ssm` と `direct` 以外の値ならエラーにして終了する。ssh は
ProxyCommand に自分の環境変数を渡すので、`TEMT_LOGIN=direct ssh <名前>` でその
接続だけ経路を変えられる。一方が使えないときに他方へ自動で
切り替えることはしない。

どちらの経路でも、まず `start` と同じ条件でインスタンスを探す
（[design/instance.md](design/instance.md#探す)）。つなぐインスタンスは、この 1 回の
探索で決め、アドレスもそのインスタンスのものを使う。known_hosts が指すインスタンスと
接続先のアドレスが、別のインスタンスのものにならないようにするためである。

- 無ければ、`start` するよう告げて終了する。2 台以上なら、`start` と同じく列挙し、
  余分なものを終了してからつなぎ直すよう告げて終了する。
- `pending` なら、`running` になるまで待つ。
- `stopped` か `stopping` なら、`start` するよう告げて終了する。

続けて、経路でつなげるかを確かめる。`ssm` なら SSM エージェントが `Online` と
報告しているか、`direct` ならパブリック IPv4 アドレスが付いていて、そのアドレスの
ポートに TCP でつながるか（1 回の試みは 5 秒まで）である。インスタンスが起動して
間もなければ（`pending` だったか、起動から 5 分の内なら）、つなげるようになるまで
待つ。再開したインスタンスの起動時刻は再開した時刻なので、再開して間もないときも
待つ。`ssm` で待つ `Online` は、`start` と同じく起動時刻より後の報告だけを数える。
`ssm` では、さらに sshd の待ち受けポートを揃える関連付けが実行し終わるまで待つ
（[design/sshd-ports.md](design/sshd-ports.md#起動直後)）。待つあいだは標準エラー
出力に知らせ、ssh がそれを画面に出す。起動から時間が
たっていれば待たず、つなげなければ手がかりを添えて終了する。`ssm` ならエージェント
の状態を見るよう添える。`direct` なら、接続を拒まれたときは sshd が受け付けていない
と、時間切れなどのときは受信規則を見るよう添える。待って締め切りを過ぎたときも、
最後につながらなかった理由で同じように添える。次に known_hosts を用意する
（[design/ssh.md](design/ssh.md#known_hosts)）。そのうえで、

- `ssm` なら `aws ssm start-session` を `exec` する。
- `direct` なら、確かめでつないだ TCP の接続をそのまま使い、接続と標準入出力の
  あいだでバイト列を中継する。標準入力が終わったら接続の送る側だけを閉じ、
  インスタンスが接続を閉じたら終了する。中継の途中で接続が切れたときも、閉じた
  ときと同じく何も告げずに終了する。切れたことは ssh が知らせる。ssh は終わるときに
  `proxy` へ SIGHUP を送るので、`proxy` もそこで終了する。接続には、既定の ssh が
  自分で TCP につなぐときと同じく `TCP_NODELAY` と `SO_KEEPALIVE` を付ける。
